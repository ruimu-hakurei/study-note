**堆（Heap）和栈（Stack）是嵌入式、C 语言、FreeRTOS 里最容易混，但又非常核心的两个概念。**

先记住最粗的一句话：

> **栈：程序自动管理，主要放函数调用和局部变量。**  
> **堆：程序运行时动态申请，用多少申请多少，通常需要自己管理释放。**

---

## 一、先从一个普通 C 程序看

假设：

```
int g_value = 100;

void func(int x)
{
    int a = 10;

    int *p = malloc(100);

    // ...

    free(p);
}
```

这里其实涉及了好几个区域：

```
Flash
├── func() 的程序代码
└── 其他机器指令

SRAM
├── .data
│   └── g_value = 100
│
├── Heap
│   └── malloc(100) 申请出来的空间
│
└── Stack
    ├── 参数 x
    ├── 局部变量 a
    └── 指针变量 p
```

特别注意：

```
int *p = malloc(100);
```

其实有两个东西：

```
p 这个指针变量
→ Stack

p 指向的 100 字节
→ Heap
```

这是第一个最重要的区别。

---

# 二、栈 Stack 到底是什么？

栈可以想象成一摞盘子。

```
       ↑ 栈顶

     ┌───────┐
     │ 盘子4 │
     ├───────┤
     │ 盘子3 │
     ├───────┤
     │ 盘子2 │
     ├───────┤
     │ 盘子1 │
     └───────┘
```

你只能：

```
从最上面放
从最上面拿
```

这种结构叫：

> **LIFO：Last In, First Out，后进先出。**

函数调用特别适合这种结构。

---

## 三、函数调用为什么需要栈？

比如：

```
void A(void)
{
    int a = 10;

    B();
}

void B(void)
{
    int b = 20;

    C();
}

void C(void)
{
    int c = 30;
}
```

程序运行：

```
main()
 ↓
A()
 ↓
B()
 ↓
C()
```

栈可能变成：

```
           Stack

        ┌───────────┐
        │ C 的数据   │ ← 当前栈顶
        │ c = 30    │
        ├───────────┤
        │ B 的数据   │
        │ b = 20    │
        ├───────────┤
        │ A 的数据   │
        │ a = 10    │
        ├───────────┤
        │ main      │
        └───────────┘
```

然后 `C()` 返回：

```
C 的栈空间释放
```

变成：

```
        ┌───────────┐
        │ B 的数据   │
        ├───────────┤
        │ A 的数据   │
        ├───────────┤
        │ main      │
        └───────────┘
```

然后 `B()` 返回：

```
B 的空间又释放
```

所以栈特别适合函数调用，因为：

> 函数进入时分配，函数返回时自动回收。

你根本不需要：

```
free(a);
```

---

# 四、栈里面到底存什么？

一个函数调用时，栈里通常可能包含：

```
普通局部变量

函数参数

返回地址

部分CPU寄存器现场

函数调用过程中临时数据
```

例如：

```
void Calculate(int x, int y)
{
    int result;
    int buffer[50];

    ...
}
```

这些：

```
x
y
result
buffer
```

都会消耗这个函数所处的栈。

但具体某个变量是否真的落到 RAM 栈里，由编译器决定。

比如：

```
int a = 1;
```

编译器可能直接让：

```
a
```

一直待在 CPU 寄存器里。

所以我们学习时说：

> “普通局部变量属于栈上的对象”

是正确的程序模型，但实际优化后的机器代码不一定真的每个变量都写进 SRAM。

---

# 五、什么叫“栈帧”？

每调用一个函数，通常会建立一块属于这个函数的栈空间。

这一块叫：

> **Stack Frame，栈帧。**

例如：

```
Stack

┌─────────────────┐
│ C() Stack Frame │
├─────────────────┤
│ B() Stack Frame │
├─────────────────┤
│ A() Stack Frame │
├─────────────────┤
│ main Stack      │
└─────────────────┘
```

当 `C()`：

```
return;
```

它的 Stack Frame 被弹掉。

---

# 六、栈为什么非常快？

因为分配栈空间通常只是修改一个寄存器：

> **SP，Stack Pointer，栈指针。**

假设原来：

```
SP = 0x20001000
```

函数需要 40 字节。

CPU 可能类似：

```
SP
↓
移动40字节
```

就完成了分配。

函数返回，再把 SP 恢复。

所以栈的分配和释放通常：

```
非常快
非常简单
时间比较确定
```

这对实时嵌入式系统非常好。

---

# 七、那么栈有什么缺点？

最大的问题：

> **空间有限。**

例如 Task 栈只有：

```
512 Byte
```

结果你写：

```
void Task(void *arg)
{
    uint8_t buffer[1000];

    while (1)
    {
    }
}
```

光：

```
buffer[1000]
```

就要大约：

```
1000 Byte
```

已经超过栈大小。

于是：

> **Stack Overflow，栈溢出。**

---

# 八、栈溢出到底是什么？

假设给 Stack 预留：

```
┌──────────────────┐
│     Stack        │
│  只有512 Byte    │
└──────────────────┘
```

但是实际函数用了：

```
700 Byte
```

那么它就可能继续往外写：

```
正常Stack
────────────
越界
↓
破坏别的RAM
```

可能破坏：

```
其他变量
TCB
Queue
另一个Task的Stack
```

最后表现可能非常奇怪：

```
HardFault

随机死机

变量莫名变化

任务突然不运行

程序跑飞
```

所以 FreeRTOS 里面：

```
configCHECK_FOR_STACK_OVERFLOW
```

非常重要。

---

# 九、递归为什么容易爆栈？

比如：

```
void func(int n)
{
    int buffer[100];

    if (n > 0)
    {
        func(n - 1);
    }
}
```

调用：

```
func(100)
```

意味着：

```
func()
 ↓
func()
 ↓
func()
 ↓
func()
...
```

每一层都有自己的：

```
buffer[100]
```

所以栈空间不断增加。

这就是为什么嵌入式开发中通常比较谨慎使用深递归。

---

# 十、再说 Heap 堆

Heap 完全是另一种思路。

例如：

```
uint8_t *buffer;

buffer = malloc(1000);
```

意思是：

> “我现在需要 1000 字节，请从 Heap 给我找一块。”

Heap 管理器就在一大片 RAM 中寻找：

```
┌──────────────────────┐
│      Heap            │
│                      │
│ ███ 已使用           │
│                      │
│ □□□ 空闲             │
│                      │
│ ███ 已使用           │
│                      │
└──────────────────────┘
```

找到一块足够大的空闲区域后，把地址给你：

```
buffer = 地址;
```

---

# 十一、Heap 和 Stack 的生命周期完全不同

看这个：

```
void func(void)
{
    int a = 10;

    int *p = malloc(100);
}
```

`func()` 结束后：

```
a
→ 自动消失

p这个指针变量
→ 自动消失
```

但是：

```
malloc出来的100字节
```

**不会因为函数返回自动释放。**

如果你没有：

```
free(p);
```

那么它仍然占着 Heap。

但问题是：

```
p已经没了
```

你甚至找不到这块内存了。

这就是：

> **Memory Leak，内存泄漏。**

---

# 十二、内存泄漏举例

```
while (1)
{
    uint8_t *p = malloc(100);
}
```

每循环一次：

```
Heap少100字节
```

于是：

```
10000 Byte
↓
9900
↓
9800
↓
9700
↓
...
↓
0
```

最后：

```
malloc(100)
```

失败，返回：

```
NULL
```

所以标准写法通常至少应该检查：

```
uint8_t *p = malloc(100);

if (p != NULL)
{
    // 使用

    free(p);
}
```

---

# 十三、Heap 为什么比 Stack 灵活？

因为你可以运行时才决定大小。

例如：

```
uint32_t len = ReceivePacketLength();

uint8_t *buffer = malloc(len);
```

如果：

```
len = 100
```

申请100。

下一次：

```
len = 5000
```

申请5000。

这就是：

> **Dynamic Allocation，动态内存分配。**

而：

```
uint8_t buffer[1000];
```

这个大小一般在编译时已经固定。

---

# 十四、Heap 最大的问题：碎片

这是嵌入式里非常重要的问题。

假设 Heap：

```
AAAAAAAA BBBBBBBB CCCCCCCC
```

分别是三块已分配内存。

现在释放：

```
A
C
```

变成：

```
空闲空闲 BBBBBBBB 空闲空闲
```

虽然：

```
总空闲内存
```

可能很多。

但是如果你需要一整块特别大的连续内存：

```
XXXXXXXXXXXX
```

可能找不到。

因为空闲空间被切碎了。

这叫：

> **Memory Fragmentation，内存碎片。**

---

# 十五、为什么 Heap 分配通常比 Stack 慢？

Stack：

```
移动一下SP
```

基本就可以。

Heap：

```
malloc()
 ↓
寻找合适空闲块
 ↓
检查大小
 ↓
拆分内存块
 ↓
修改管理结构
 ↓
返回地址
```

`free()` 可能还要：

```
标记为空闲
↓
合并相邻空闲块
```

所以：

```
Heap
```

通常比 Stack：

```
复杂
慢
时间不那么固定
```

这也是实时系统特别关注的地方。

---

# 十六、嵌入式为什么特别在意 Heap？

PC 上：

```
16GB RAM
32GB RAM
```

碎一点可能没那么明显。

STM32F103：

```
几十KB SRAM
```

如果一个地方泄漏：

```
500 Byte
```

已经很可观了。

所以嵌入式开发会非常关注：

```
内存泄漏
碎片
峰值使用量
分配失败
```

---

# 十七、Stack 和 Heap 对比

|项目|Stack 栈|Heap 堆|
|---|---|---|
|谁管理|编译器/运行时自动管理|内存分配器 + 程序员|
|分配方式|函数进入自动使用|`malloc()`|
|释放方式|函数退出自动释放|`free()`|
|速度|通常很快|通常更慢|
|大小|通常较有限|相对灵活|
|生命周期|通常跟函数调用有关|由你决定|
|碎片|基本没有传统Heap碎片问题|可能产生|
|典型内容|局部变量、函数现场|动态数组、动态对象|
|常见问题|Stack Overflow|Leak / Fragmentation|

这张表最好真的理解，而不是背。

# 十八、现在进入 FreeRTOS：事情开始变得更有意思

普通裸机 C 程序，你可能粗略想：

```
一个Stack
+
一个Heap
```

但是 FreeRTOS 有：

```
Task1
Task2
Task3
```

每一个 Task 都相当于一条独立的程序执行流。

那么问题来了：

> 如果 Task1 和 Task2 同时调用函数，它们共用一个 Stack 行不行？

不行。

所以：

> **每一个 FreeRTOS Task 都必须拥有自己的 Stack。**

---

# 十九、FreeRTOS 每个任务一块独立栈

例如：

```
xTaskCreate(TaskA, "A", 128, NULL, 1, NULL);

xTaskCreate(TaskB, "B", 256, NULL, 2, NULL);
```

概念上：

```
TaskA
└── Stack A

TaskB
└── Stack B
```

因为：

```
TaskA可能正在：
FunctionA()
→ FunctionB()
→ FunctionC()

TaskB可能正在：
MotorControl()
→ PID()
```

它们必须各自保存：

```
局部变量
返回地址
寄存器现场
```

---

# 二十、这就是为什么任务切换能工作

假设：

```
Task A正在运行
```

它的：

```
SP
```

指向：

```
Task A Stack
```

然后调度器切到 Task B。

FreeRTOS 保存：

```
Task A 的 SP
```

然后把 CPU 的 SP 换成：

```
Task B 的 SP
```

恢复 Task B 的寄存器现场。

于是：

```
Task A Stack
        ↑
保存A执行到了哪里

Task B Stack
        ↑
保存B执行到了哪里
```

所以：

> **Task Stack 是 FreeRTOS 实现上下文切换的核心基础之一。**

这就和你之前学的 `PendSV` 连上了。

---

# 二十一、`xTaskCreate()` 的 Stack 参数是什么意思？

例如：

```
xTaskCreate(
    MotorTask,
    "Motor",
    256,
    NULL,
    2,
    NULL
);
```

这里：

```
256
```

就是 Task Stack Depth。

但是注意：

> **通常不是256 Byte。**

而是：

```
256 个 StackType_t
```

在 STM32F103 Cortex-M3 中：

```
StackType_t通常 = 32 bit = 4 Byte
```

所以大致：

```
256 × 4
=
1024 Byte
```

也就是：

```
MotorTask大约1KB Stack
```

---

# 二十二、Task Stack 到底从哪里来？

如果你使用：

```
xTaskCreate()
```

动态创建任务，

并且 FreeRTOS 用：

```
heap_4.c
```

那么通常：

```
FreeRTOS Heap
↓
申请TCB
+
申请Task Stack
```

例如：

```
FreeRTOS Heap

┌────────────────────┐
│ TaskA TCB          │
├────────────────────┤
│ TaskA Stack        │
├────────────────────┤
│ TaskB TCB          │
├────────────────────┤
│ TaskB Stack        │
├────────────────────┤
│ Queue              │
├────────────────────┤
│ Mutex              │
└────────────────────┘
```

所以非常关键：

> **FreeRTOS Task 的 Stack 可以是从 FreeRTOS Heap 中动态分配出来的。**

---

# 二十三、这不会矛盾吗？

你可能会觉得：

> “等等，Stack 怎么会在 Heap 里面？”

这里必须区分：

**“它从哪里分配”**

和

**“它拿来做什么”**

是两回事。

例如 FreeRTOS 从：

```
ucHeap[]
```

里面切出：

```
1024 Byte
```

然后告诉 TaskA：

> “这一块以后就是你的 Stack。”

那么：

```
物理来源：
FreeRTOS Heap区域

逻辑用途：
Task A Stack
```

所以完全不矛盾。

---

# 二十四、FreeRTOS Heap 和 `malloc()` Heap 不一定一样

这点一定要记。

标准 C：

```
malloc()
free()
```

FreeRTOS：

```
pvPortMalloc()
vPortFree()
```

如果你使用：

```
heap_4.c
```

FreeRTOS 通常管理自己的：

```
ucHeap[]
```

例如配置：

```
#define configTOTAL_HEAP_SIZE (20 * 1024)
```

就是：

```
给FreeRTOS大约20KB Heap
```

然后：

```
xTaskCreate()
xQueueCreate()
xSemaphoreCreateMutex()
```

等会从这里分配。

---

# 二十五、为什么你设置 `configTOTAL_HEAP_SIZE` 后任务会创建失败？

假设：

```
FreeRTOS Heap = 10KB
```

你创建：

```
Task1 Stack 2KB
Task2 Stack 2KB
Task3 Stack 2KB
Task4 Stack 2KB
```

再加：

```
TCB
Queue
Semaphore
系统开销
```

可能已经快满。

于是：

```
xTaskCreate(...)
```

需要继续申请：

```
2KB
```

结果：

```
Heap剩余不足
```

那么：

```
xTaskCreate()
```

可能返回：

```
errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY
```

所以：

> Task 栈大小和 FreeRTOS Heap 消耗直接相关。

---

# 二十六、但是 Stack 不是越大越好吗？

当然不是。

比如：

```
Task只需要300 Byte
```

你却给：

```
4096 Byte
```

意味着大量 SRAM 白白浪费。

假设你有：

```
10个Task
```

每个多给：

```
3KB
```

那就是：

```
30KB RAM
```

直接没了。

所以真正工程里：

> **Task Stack 要留裕量，但不能盲目给巨大。**

---

# 二十七、怎么看 Task Stack 够不够？

FreeRTOS 有：

```
uxTaskGetStackHighWaterMark()
```

或者新版相关接口。

它能告诉你：

> Task 历史上距离把栈用光最近的时候，还剩多少。

比如：

```
TaskA Stack = 256 words
```

运行一段时间以后：

```
High Water Mark = 80 words
```

说明最危险的时候仍然大概剩：

```
80 × 4 = 320 Byte
```

有一定余量。

如果只有：

```
2 words
```

那就非常危险了。

---

# 二十八、为什么 `printf()` 很容易把 Task Stack 吃掉？

例如：

```
void Task(void *arg)
{
    while (1)
    {
        printf("value = %f\r\n", value);
    }
}
```

看上去代码没多少。

但：

```
printf
浮点格式化
C库函数调用
```

内部可能调用很多层函数，使用不少局部变量。

因此 Stack 消耗可能远比你想象的大。

所以嵌入式里：

```
printf + float
```

经常是 Stack 和 Flash 消耗大户。

---

# 二十九、大数组放 Stack 还是 Heap？

比如：

```
uint8_t imageBuffer[10000];
```

如果放在 Task 函数内部：

```
void Task(void *arg)
{
    uint8_t imageBuffer[10000];

    ...
}
```

直接吃：

```
约10KB Task Stack
```

对于 STM32 可能非常夸张。

可以考虑：

```
static uint8_t imageBuffer[10000];
```

那么：

```
.bss
```

或者动态：

```
uint8_t *buffer = pvPortMalloc(10000);
```

从 FreeRTOS Heap。

但应该选哪一种，要看：

```
生命周期
实时性
RAM总量
是否允许动态分配
多个Task是否共享
```

不是简单“Heap一定好”。

---

# 三十、实时系统为什么有时候不喜欢运行中频繁 malloc？

因为实时系统特别关心：

> **这段代码最坏需要多少时间？**

Stack：

```
移动SP
```

时间很好预测。

动态 Heap：

```
找空闲块
拆分
合并
```

耗时更依赖当前内存状态。

而且长期：

```
malloc/free
malloc/free
malloc/free
```

还可能产生碎片。

所以很多安全要求比较高的嵌入式系统喜欢：

```
系统启动阶段
↓
把任务、Queue、Buffer都建好
↓
之后运行期间尽量不再动态创建/删除
```

甚至完全使用：

```
xTaskCreateStatic()
```

这种静态分配方式。

---

# 三十一、`xTaskCreateStatic()` 又是什么意思？

例如提前准备：

```
StaticTask_t taskTCB;

StackType_t taskStack[256];
```

然后：

```
xTaskCreateStatic(
    Task,
    "Task",
    256,
    NULL,
    1,
    taskStack,
    &taskTCB
);
```

这时候不是：

```
FreeRTOS Heap
↓
动态申请
```

而是：

> “这块 TCB 和 Stack 内存我已经准备好了，你直接用。”

优点：

```
内存大小编译时确定
不会运行时申请失败
没有动态分配碎片问题
```

这就是：

```
configSUPPORT_STATIC_ALLOCATION
```

背后的意义。

---

# 三十二、最后用一个机器人任务把 Heap 和 Stack 全串起来

假设：

```
void IMUTask(void *arg)
{
    float gyro[3];
    float accel[3];

    uint8_t *buffer = pvPortMalloc(512);

    while (1)
    {
        ReadIMU(gyro, accel);

        vTaskDelay(1);
    }
}
```

假设：

```
xTaskCreate(
    IMUTask,
    "IMU",
    256,
    NULL,
    3,
    NULL
);
```

那么内存大概：

```
FreeRTOS Heap
│
├── IMUTask TCB
│
├── IMUTask Stack
│       │
│       ├── gyro[3]
│       ├── accel[3]
│       ├── buffer这个指针
│       ├── 函数调用现场
│       └── CPU上下文
│
└── pvPortMalloc(512)得到的Buffer
        ↑
        │
        buffer 指向这里
```

注意这里非常有意思：

```
整个Task Stack
```

本身可能是从 FreeRTOS Heap 切出来的。

而 Task 运行后又：

```
pvPortMalloc(512)
```

从剩余的 FreeRTOS Heap 再申请一块。

# 最后形成一张真正适合 FreeRTOS 的内存图

```
                    STM32 SRAM
                         │
       ┌─────────────────┼─────────────────┐
       ↓                 ↓                 ↓

     .data             .bss           系统栈等
       │                 │
 全局有初值        全局零/未初始化
                         │
                         └── 可能包含 ucHeap[]
                                  │
                                  ↓
                           FreeRTOS Heap
                                  │
               ┌──────────────────┼──────────────────┐
               ↓                  ↓                  ↓
          Task1 TCB          Task1 Stack            Queue
          Task2 TCB          Task2 Stack            Mutex
                                                   Buffer
```

而 Task Stack 内部：

```
Task1 Stack
│
├── 局部变量
├── 函数参数
├── 函数调用现场
├── 返回地址
└── 保存的CPU寄存器
```

所以以后你看到两个报错，脑子里应该完全区分：

```
Stack Overflow
```

意思：

> **某个任务自己的栈不够。**

而：

```
Malloc Failed
```

通常意味着：

> **FreeRTOS Heap 整体可分配内存不够。**

这两个问题完全不是一回事，但它们又有联系：**如果动态创建 Task，给任务的 Stack 越大，就越消耗 FreeRTOS Heap。**
