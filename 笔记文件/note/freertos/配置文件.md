# FreeRTOSConfig.h 配置文件：从原理到 STM32F103 实战

> [!abstract] 一句话理解
> `FreeRTOSConfig.h` 是 FreeRTOS 内核的“项目级设计说明书”：它告诉通用内核本项目如何调度、怎样计时、给多少内存、开放哪些功能，以及哪些中断可以调用 FreeRTOS API。

> [!warning] 先记住
> 不要从其他工程整份复制 `FreeRTOSConfig.h`。MCU 时钟、FreeRTOS 版本、移植层、堆实现和中断优先级只要有一项不同，照抄都可能造成编译错误或隐蔽的运行故障。

## 1. 它在编译过程中做什么

FreeRTOS 内核是一套通用源码，不知道当前项目使用什么 MCU、CPU 跑多快、需要多少优先级，也不知道是否使用互斥锁和软件定时器。

编译 `tasks.c`、`queue.c` 等内核文件时，`FreeRTOS.h` 会包含：

```c
#include "FreeRTOSConfig.h"
```

内核随后根据配置宏选择代码路径：

```c
#if ( configUSE_PREEMPTION == 1 )
    /* 编译抢占式调度相关逻辑 */
#endif

#if ( configUSE_MUTEXES == 1 )
    /* 编译互斥锁相关逻辑 */
#endif
```

因此，配置文件不仅保存数值，还会影响：

- 哪些内核功能参与编译；
- 调度器以什么规则运行；
- SysTick 多久产生一次系统节拍；
- FreeRTOS 使用多少 RAM；
- 中断和内核之间的安全边界。

### 文件放在哪里

它没有强制的固定目录，只要编译器能通过 Include Path 找到即可。STM32CubeIDE/CubeMX 工程中常见位置是：

```text
Core/Inc/FreeRTOSConfig.h
```

典型工程结构：

```text
Project
├─ Core
│  ├─ Inc
│  │  ├─ main.h
│  │  └─ FreeRTOSConfig.h
│  └─ Src
├─ Drivers
└─ Middlewares
   └─ Third_Party
      └─ FreeRTOS
```

如果出现下面的错误，先检查文件是否存在，再检查包含路径：

```text
fatal error: FreeRTOSConfig.h: No such file or directory
```

## 2. 五类配置总览

| 类别 | 解决的问题 | 代表宏 |
|---|---|---|
| 时间系统 | CPU 多快、Tick 多久一次、Tick 能表示多长时间 | `configCPU_CLOCK_HZ`、`configTICK_RATE_HZ`、`configTICK_TYPE_WIDTH_IN_BITS` |
| 调度与任务 | 是否抢占、是否时间片轮转、优先级和任务名范围 | `configUSE_PREEMPTION`、`configUSE_TIME_SLICING`、`configMAX_PRIORITIES` |
| 内存 | 能否动态/静态创建对象、FreeRTOS 堆多大、最小任务栈多大 | `configSUPPORT_*_ALLOCATION`、`configTOTAL_HEAP_SIZE`、`configMINIMAL_STACK_SIZE` |
| 内核功能 | 是否使用互斥锁、任务通知、软件定时器、Hook | `configUSE_MUTEXES`、`configUSE_TASK_NOTIFICATIONS`、`configUSE_TIMERS` |
| 中断与安全 | 哪些中断可以调用 `FromISR` API、怎样发现错误 | `configMAX_SYSCALL_INTERRUPT_PRIORITY`、`configASSERT`、栈溢出检测 |

阅读陌生工程时，建议先按这个顺序看：

```text
CPU 时钟和 Tick
    ↓
调度方式与任务优先级
    ↓
堆与栈
    ↓
中断优先级边界
    ↓
启用的功能和诊断开关
```

## 3. 时间系统：CPU 时钟、Tick 与 TickType_t

这三个配置共同组成 FreeRTOS 的时间基础：

```text
configCPU_CLOCK_HZ
        ↓ 决定产生 Tick 所需的硬件计数
configTICK_RATE_HZ
        ↓ 决定每秒增加多少个 Tick
TickType_t 的位宽
        ↓ 决定 Tick 计数多久回绕
延时、超时、阻塞等待
```

### 3.1 `configCPU_CLOCK_HZ`：内核实际时钟

```c
#define configCPU_CLOCK_HZ    72000000UL
```

它表示 Cortex-M 内核实际运行频率，单位是 Hz。在 STM32F103 的常见配置中，它对应时钟树里的 **HCLK/Core Clock**，不是随便选择一个外设时钟。

```text
时钟源 HSI/HSE
      ↓
PLL（可选倍频）
      ↓
SYSCLK
      ↓ AHB Prescaler
HCLK / Cortex-M3 Core Clock
      ↓
configCPU_CLOCK_HZ
```

> [!note] 更稳妥的写法
> 某些工程模板使用 `SystemCoreClock`，避免频率在两个地方重复写死：

```c
extern uint32_t SystemCoreClock;
#define configCPU_CLOCK_HZ    ( SystemCoreClock )
```

具体能否这样写要看启动代码和移植层何时更新 `SystemCoreClock`。以当前工程模板为准。

#### STM32F103：默认 8 MHz

```text
HSI = 8 MHz
  ↓
SYSCLK = 8 MHz
  ↓ AHB ÷1
HCLK = 8 MHz
```

对应：

```c
#define configCPU_CLOCK_HZ    8000000UL
```

#### STM32F103：常见最高 72 MHz 配置

假设开发板使用 8 MHz HSE：

```text
HSE = 8 MHz
  ↓ PLL ×9
SYSCLK = 72 MHz
  ↓ AHB ÷1
HCLK = 72 MHz  →  configCPU_CLOCK_HZ
  ├─ APB1 ÷2 → PCLK1 = 36 MHz
  └─ APB2 ÷1 → PCLK2 = 72 MHz
```

对应：

```c
#define configCPU_CLOCK_HZ    72000000UL
```

> [!warning] 不要填 `36000000`
> `36 MHz` 是 APB1 外设时钟，不是 Cortex-M3 内核时钟。FreeRTOS 这里通常需要 HCLK/Core Clock。

#### CubeMX 中从 8 MHz 配到 72 MHz

1. 双击工程的 `.ioc` 文件。
2. 在 `System Core → RCC` 中启用 HSE；若板上是晶振，通常选择 `Crystal/Ceramic Resonator`。
3. 打开 `Clock Configuration`，确认输入的 HSE 频率与开发板实物一致。
4. 选择 HSE 作为 PLL 输入，PLL 倍频设为 `×9`。
5. 选择 `PLLCLK` 作为 SYSCLK 来源。
6. AHB Prescaler 设为 `÷1`，得到 HCLK 72 MHz。
7. APB1 Prescaler 设为 `÷2`，得到 36 MHz；APB2 可设为 `÷1`，得到 72 MHz。
8. 生成代码，确认 `SystemClock_Config()` 已更新。
9. 将 `configCPU_CLOCK_HZ` 与最终 HCLK 保持一致，然后完整重新编译。

如果 CubeMX 时钟图出现红色，通常表示某个总线或外设超过器件上限，不要强行生成。

可在调试器里观察 `SystemCoreClock`，或将 MCO 输出到引脚后用示波器测量，以确认实际频率。

#### 配错会发生什么

假设 CPU 实际是 72 MHz，配置文件却仍写 8 MHz，移植层计算出的 SysTick 重装值可能错误，于是：

- `vTaskDelay(pdMS_TO_TICKS(1000))` 不再接近 1 秒；
- 软件定时器和超时判断整体变快或变慢；
- 调度 Tick 的频率与预期不同。

> [!note] 版本与移植层差异
> 部分 STM32/CubeMX 工程会用 HAL、CMSIS-RTOS 或单独的 `configSYSTICK_CLOCK_HZ` 配置 Tick 时钟。判断依据应是当前工程的 FreeRTOS 移植代码，而不是只看宏名。

### 3.2 `configTICK_RATE_HZ`：每秒多少个系统节拍

```c
#define configTICK_RATE_HZ    1000U
```

表示每秒产生 1000 个 Tick：

```text
Tick 周期 = 1 / 1000 s = 1 ms
```

常见取值：

| Tick 频率 | 一个 Tick | 特点 |
|---:|---:|---|
| 100 Hz | 10 ms | 中断开销较低，时间粒度较粗 |
| 500 Hz | 2 ms | 折中 |
| 1000 Hz | 1 ms | STM32 教学和通用控制项目常见 |

Tick 越高不代表系统越快。频率越高，Tick ISR 执行越频繁，CPU 开销和功耗也可能越高。应根据系统需要的最小延时粒度选择。

延时建议写成：

```c
vTaskDelay(pdMS_TO_TICKS(500));   // 表达“500 ms”，不依赖 Tick 恰好为 1 ms
```

而不是：

```c
vTaskDelay(500);                  // 实际含义是 500 Tick，不一定是 500 ms
```

对于周期任务，`vTaskDelayUntil()` 比连续调用 `vTaskDelay()` 更不容易积累周期漂移：

```c
void SensorTask(void *argument)
{
    TickType_t last_wake = xTaskGetTickCount();

    for (;;)
    {
        ReadSensor();
        vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(10)); // 以固定节拍运行
    }
}
```

### 3.3 `configTICK_TYPE_WIDTH_IN_BITS`：Tick 计数位宽

新版本 FreeRTOS 可能使用：

```c
#define configTICK_TYPE_WIDTH_IN_BITS    TICK_TYPE_WIDTH_32_BITS
```

旧版本常见：

```c
#define configUSE_16_BIT_TICKS           0  // 0 通常表示使用 32 位 Tick
```

二者作用相近，但属于不同版本的配置接口。**只使用当前 FreeRTOS 版本要求的写法，不要同时凭空添加。**

`TickType_t` 是保存 Tick 数和超时时间的无符号整数类型。以 1000 Hz Tick 为例：

| 位宽 | 最大计数 | 大约多久回绕一次 |
|---:|---:|---:|
| 16 位 | 65,535 | 65.536 秒 |
| 32 位 | 4,294,967,295 | 49.7 天 |

#### 回绕不等于系统崩溃

无符号计数到最大值后会从 0 继续。FreeRTOS 内核的延时和超时逻辑会处理正常回绕；问题通常来自应用层自己写了错误比较：

```c
// 不推荐：跨越回绕点时，绝对大小比较可能失效
if (xTaskGetTickCount() > deadline)
{
    /* timeout */
}
```

短时间间隔可使用无符号差值：

```c
TickType_t start = xTaskGetTickCount();

if ((TickType_t)(xTaskGetTickCount() - start) >= pdMS_TO_TICKS(500))
{
    /* 已经过了至少 500 ms；差值写法可自然跨越一次回绕 */
}
```

更推荐直接使用 FreeRTOS 的阻塞、队列、信号量和软件定时器 API，让内核管理超时。

`portMAX_DELAY` 的行为还与 Tick 位宽以及 `INCLUDE_vTaskSuspend` 等配置有关。不要把它无条件理解成“永久等待”；应查当前版本的 API 说明和配置。

## 4. 调度与任务配置

### 4.1 `configUSE_PREEMPTION`

```c
#define configUSE_PREEMPTION    1
```

- `1`：抢占式调度。更高优先级任务进入 Ready 后，可以抢占当前低优先级任务。
- `0`：协作式调度。当前任务通常需要主动阻塞或让出 CPU，其他任务才有机会运行。

STM32 的常规 FreeRTOS 项目通常使用抢占式调度。

```text
低优先级任务正在 Running
        ↓
高优先级任务因队列/中断变为 Ready
        ↓
调度器切换到高优先级任务
```

### 4.2 `configUSE_TIME_SLICING`

```c
#define configUSE_TIME_SLICING    1
```

开启后，多个**相同优先级且同时 Ready** 的任务可按 Tick 轮流获得 CPU。

它不能让低优先级任务与高优先级任务平分 CPU。只要高优先级任务一直不阻塞，低优先级任务仍可能长期得不到运行机会。

> [!tip] 任务设计原则
> 任务完成一轮工作后应通过队列、通知、信号量或 `vTaskDelay()` 进入阻塞态，不要让高优先级任务无限空转。

### 4.3 `configMAX_PRIORITIES`

```c
#define configMAX_PRIORITIES    5
```

表示可用任务优先级为：

```text
0、1、2、3、4
```

FreeRTOS **任务优先级数字越大，优先级越高**。这与 Cortex-M NVIC 的“数字越小越紧急”正好相反。

`configMAX_PRIORITIES` 越大，内核用于记录 Ready 任务的结构通常也会增加。只配置项目实际需要的档位。

一个简单的任务优先级示例：

| 任务 | FreeRTOS 优先级 | 设计理由 |
|---|---:|---|
| Idle Task | 0 | 内核空闲任务 |
| 日志输出 | 1 | 不应阻挡控制逻辑 |
| 界面刷新 | 2 | 有周期要求但不紧急 |
| 传感器处理 | 3 | 数据到达后及时处理 |
| 安全控制 | 4 | 只做短而关键的处理 |

不要仅凭“重要”就提高优先级；还要分析阻塞关系、执行时间和共享资源。

### 4.4 `configMAX_TASK_NAME_LEN`

```c
#define configMAX_TASK_NAME_LEN    16
```

限制任务名缓冲区长度，通常包含字符串结尾的 `\0`。任务名主要用于调试和跟踪，太短难以辨认，太长会占用更多 RAM。

## 5. 内存与栈配置

### 5.1 动态与静态分配

```c
#define configSUPPORT_DYNAMIC_ALLOCATION    1
#define configSUPPORT_STATIC_ALLOCATION     1
```

- 动态创建：使用 `xTaskCreate()`、`xQueueCreate()` 等，由 FreeRTOS 堆提供内存。
- 静态创建：使用 `xTaskCreateStatic()`、`xQueueCreateStatic()` 等，由应用提供内存缓冲区。

二者可以同时开启。静态分配便于精确控制内存和生命周期；动态分配使用更灵活。

### 5.2 `configTOTAL_HEAP_SIZE`

```c
#define configTOTAL_HEAP_SIZE    (20U * 1024U)
```

这是 FreeRTOS 动态分配器可管理的堆大小，**不是 STM32 的全部 RAM**。

```text
MCU SRAM
├─ .data / .bss 全局与静态变量
├─ 启动栈/主栈
├─ C 库可能使用的堆
└─ FreeRTOS Heap
   ├─ 任务 TCB
   ├─ 任务栈
   ├─ 队列/信号量/互斥锁
   └─ 软件定时器等动态对象
```

它是否生效、怎样布局，取决于工程选择的 `heap_1.c`～`heap_5.c`。例如使用 `heap_3.c` 时，内核转而包装标准库的 `malloc/free`，不能再机械地用同一种方式理解 `configTOTAL_HEAP_SIZE`。

可以观察：

```c
size_t free_now = xPortGetFreeHeapSize();
size_t free_min = xPortGetMinimumEverFreeHeapSize();
```

`free_min` 是启动以来的最小剩余堆，更适合判断历史峰值是否逼近极限。

### 5.3 `configMINIMAL_STACK_SIZE`

```c
#define configMINIMAL_STACK_SIZE    128U
```

它主要定义 Idle Task 等最小任务栈基准。单位通常是 `StackType_t` 个数，**不一定是字节**。

在 Cortex-M3 上常见：

```text
sizeof(StackType_t) = 4 字节
128 个 StackType_t ≈ 512 字节
```

但应以当前端口的类型定义为准。

任务栈需要容纳：

- 函数局部变量；
- 函数调用链和保存的寄存器；
- 中断/上下文切换相关现场；
- 某些库函数的临时数据。

`printf()`、浮点格式化、大型局部数组和深层函数调用都可能显著增加栈需求。

任务运行后可以检查高水位：

```c
UBaseType_t remain = uxTaskGetStackHighWaterMark(NULL);
```

该返回值通常也是以 `StackType_t` 为单位，表示历史上最紧张时仍未使用的栈空间。

## 6. 内核功能开关与软件定时器

### 6.1 同步与通信功能

```c
#define configUSE_MUTEXES                 1
#define configUSE_RECURSIVE_MUTEXES       1
#define configUSE_COUNTING_SEMAPHORES     1
#define configUSE_TASK_NOTIFICATIONS      1
```

| 功能 | 典型用途 | 注意点 |
|---|---|---|
| Mutex | 多任务互斥访问 I²C、SPI、文件系统等共享资源 | 具有优先级继承；不能从 ISR 获取/释放 |
| Recursive Mutex | 同一任务需要嵌套锁定同一资源 | 获取几次就必须释放几次 |
| Counting Semaphore | 资源计数、累计事件 | 不表达数据内容 |
| Task Notification | ISR 或任务向指定任务发送轻量事件/计数/数值 | 一对一通信，高效但语义需设计清楚 |

未使用的功能可以关闭以减小代码体积，但不要因为看到宏“不熟悉”就随意关闭；先搜索工程是否调用对应 API。

### 6.2 软件定时器

```c
#define configUSE_TIMERS                1
#define configTIMER_TASK_PRIORITY       2
#define configTIMER_QUEUE_LENGTH        10
#define configTIMER_TASK_STACK_DEPTH    256
```

软件定时器不是硬件 TIM 外设。到期处理函数由 **Timer Service Task** 执行：

```text
Tick/命令改变定时器状态
        ↓
Timer Command Queue
        ↓
Timer Service Task
        ↓
执行 Timer Callback
```

- `configTIMER_TASK_PRIORITY`：定时器服务任务优先级。
- `configTIMER_QUEUE_LENGTH`：发给定时器服务任务的命令队列长度。
- `configTIMER_TASK_STACK_DEPTH`：定时器服务任务栈深度，单位通常为 `StackType_t`。

Callback 应短小、不可长期阻塞。多个软件定时器共用同一个服务任务，一个回调阻塞会拖延其他回调。

## 7. 中断优先级：最容易出错的部分

### 7.1 两套优先级数字方向相反

| 对象 | 数字越大时 | 示例 |
|---|---|---|
| FreeRTOS 任务优先级 | 越高 | 任务 4 高于任务 1 |
| Cortex-M NVIC 中断优先级 | 越低 | 中断 2 高于中断 10 |

后文说“高优先级中断”时，指 NVIC 数字较小、更加紧急的中断。

### 7.2 `configPRIO_BITS`

```c
#define configPRIO_BITS    4
```

Cortex-M3 的 NVIC 优先级寄存器通常有 8 位字段，但芯片只实现其中一部分高位。STM32F103 常见实现 4 位，因此库层可用优先级数字通常为 0～15。

优先使用 CMSIS 已提供的值：

```c
#ifdef __NVIC_PRIO_BITS
    #define configPRIO_BITS    __NVIC_PRIO_BITS
#else
    #define configPRIO_BITS    4
#endif
```

### 7.3 “库层数字”与“寄存器数字”

CMSIS/HAL 配置中断时通常使用容易阅读的 0～15：

```c
#define configLIBRARY_LOWEST_INTERRUPT_PRIORITY         15
#define configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY     5
```

FreeRTOS Cortex-M 移植层还需要把它们左移到 NVIC 寄存器实际使用的位置：

```c
#define configKERNEL_INTERRUPT_PRIORITY \
    ( configLIBRARY_LOWEST_INTERRUPT_PRIORITY << (8U - configPRIO_BITS) )

#define configMAX_SYSCALL_INTERRUPT_PRIORITY \
    ( configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY << (8U - configPRIO_BITS) )
```

不要把已经左移的寄存器值直接传给 `HAL_NVIC_SetPriority()`。

### 7.4 哪些中断可以调用 FreeRTOS API

假设：

```c
configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5
configLIBRARY_LOWEST_INTERRUPT_PRIORITY      = 15
```

则通常可理解为：

| NVIC 库层优先级 | 紧急程度 | 能否调用 FreeRTOS `...FromISR()` API |
|---:|---|---|
| 0～4 | 非常高 | **不能** |
| 5～15 | 较低 | 可以调用允许在 ISR 使用的 `...FromISR()` API |

为什么最紧急的中断反而不能调用内核 API？

FreeRTOS 在修改内核关键数据时，只屏蔽“允许调用内核 API”的那一段中断。优先级 0～4 仍能打断内核临界区，因此它们必须完全独立于内核，否则可能破坏队列、任务列表等内部结构。

```text
0 ─────────────── 最紧急
│  不可调用 FreeRTOS API
4
5 ─────────────── MAX_SYSCALL 边界
│  可调用规定的 ...FromISR() API
15 ────────────── 最不紧急
```

> [!danger] 两条硬规则
> 1. ISR 中只能调用文档明确允许的 `...FromISR()` 版本，不能调用普通任务 API。
> 2. NVIC 数字小于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 的中断，连 `...FromISR()` 也不能调用。

### 7.5 标准 ISR 通知任务模板

```c
void USART1_IRQHandler(void)
{
    BaseType_t higher_priority_task_woken = pdFALSE;

    if (USART_GetITStatus(USART1, USART_IT_RXNE) != RESET)
    {
        uint8_t byte = (uint8_t)USART_ReceiveData(USART1);

        /* 该 USART 中断的 NVIC 优先级必须位于允许调用内核 API 的范围。 */
        xQueueSendFromISR(rx_queue,
                          &byte,
                          &higher_priority_task_woken);
    }

    /* 若刚唤醒的任务优先级更高，请求在退出中断时立即切换任务。 */
    portYIELD_FROM_ISR(higher_priority_task_woken);
}
```

ISR 应只做：读取硬件、清除中断源、保存最少数据、通知任务。协议解析、日志输出和耗时计算放到任务中完成。

### 7.6 NVIC 分组

FreeRTOS 通常要求把实现的优先级位用于抢占优先级，不要在工程中途随意改优先级分组。STM32 HAL 工程常见：

```c
HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);
```

实际写法要与 HAL/CMSIS 版本和 FreeRTOS 移植层保持一致。若第三方库重新设置了分组，中断安全边界可能与预期不一致。

## 8. Hook、断言与故障检测

### 8.1 Idle Hook 与 Tick Hook

```c
#define configUSE_IDLE_HOOK    1
#define configUSE_TICK_HOOK    0
```

- Idle Hook：Idle Task 每轮可能调用，适合轻量统计或进入低功耗前的处理；不能永久阻塞。
- Tick Hook：每个 Tick 在中断上下文调用，必须非常短，不能调用会阻塞的 API。

开启后需提供对应函数，否则可能链接失败：

```c
void vApplicationIdleHook(void)
{
    /* 不得调用会让 Idle Task 阻塞的函数 */
}

void vApplicationTickHook(void)
{
    /* 中断上下文：只做极少量工作 */
}
```

### 8.2 栈溢出检测

```c
#define configCHECK_FOR_STACK_OVERFLOW    2
```

栈溢出是任务实际使用的栈超过了分配空间，可能覆盖其他任务、TCB 或全局数据，症状经常表现为“随机死机”。

开启后实现：

```c
void vApplicationStackOverflowHook(TaskHandle_t task, char *task_name)
{
    (void)task;
    (void)task_name;

    taskDISABLE_INTERRUPTS();
    for (;;)
    {
        /* 在调试器中停在这里，检查 task_name 和调用栈。 */
    }
}
```

检测只能帮助发现问题，不能替代合理估算和高水位监测。

### 8.3 动态内存分配失败 Hook

```c
#define configUSE_MALLOC_FAILED_HOOK    1
```

```c
void vApplicationMallocFailedHook(void)
{
    taskDISABLE_INTERRUPTS();
    for (;;)
    {
        /* 查看剩余堆、最小剩余堆和最近创建的对象。 */
    }
}
```

### 8.4 `configASSERT`

调试阶段强烈建议保留断言：

```c
#define configASSERT(x)                         \
    do                                          \
    {                                           \
        if ((x) == 0)                           \
        {                                       \
            taskDISABLE_INTERRUPTS();           \
            for (;;)                            \
            {                                   \
                /* 在此处打断点检查调用栈 */     \
            }                                   \
        }                                       \
    } while (0)
```

它可以尽早暴露非法中断优先级、错误参数和内核状态问题。正式产品可以把文件名、行号或错误码保存到非易失存储，但要避免断言处理本身再次依赖已损坏的系统服务。

## 9. `INCLUDE_xxx`：控制 API 是否参与编译

`INCLUDE_xxx` 宏不是运行时开关，而是决定某些可选 API 是否编译进内核：

```c
#define INCLUDE_vTaskDelay            1
#define INCLUDE_vTaskDelayUntil       1
#define INCLUDE_vTaskDelete           1
#define INCLUDE_vTaskSuspend          1
#define INCLUDE_xTaskGetSchedulerState 1
```

若调用某 API 时出现未声明或链接问题，可以检查：

1. 头文件是否正确包含；
2. 当前 FreeRTOS 版本是否提供该 API；
3. 对应 `INCLUDE_xxx` 是否为 1；
4. 内核源文件是否已加入工程。

关闭未使用 API 能略微减小代码体积，但教学和调试阶段可以先保留常用功能。

## 10. STM32F103 教学配置模板

下面模板用于理解各部分关系，不保证能原样替代当前工程自动生成的文件。开始前必须确认：

- STM32F103 实际 HCLK 是否为 72 MHz；
- FreeRTOS 版本使用哪套 Tick 位宽宏；
- 工程选用了哪个 `heap_x.c`；
- 中断处理函数映射是否由 CubeMX/CMSIS-RTOS 管理；
- `__NVIC_PRIO_BITS` 和优先级分组是否正确。

```c
#ifndef FREERTOS_CONFIG_H

/* ---------- 内存 ---------- */
#define configMINIMAL_STACK_SIZE                  128U
#define configSUPPORT_DYNAMIC_ALLOCATION          1
#define configSUPPORT_STATIC_ALLOCATION           1
#define configTOTAL_HEAP_SIZE                     (20U * 1024U)

/* ---------- 内核对象 ---------- */
#define configUSE_MUTEXES                         1
#define configUSE_RECURSIVE_MUTEXES               1
#define configUSE_COUNTING_SEMAPHORES             1
#define configUSE_TASK_NOTIFICATIONS              1

/* ---------- 软件定时器 ---------- */
#define configUSE_TIMERS                          1
#define configTIMER_TASK_PRIORITY                 2U
#define configTIMER_QUEUE_LENGTH                  10U
#define configTIMER_TASK_STACK_DEPTH              256U

/* ---------- Hook 与诊断 ---------- */
#define configUSE_IDLE_HOOK                       0

#define configUSE_MALLOC_FAILED_HOOK              1

#define configASSERT(x)                           \
    do                                            \
    {                                             \

/* ---------- Cortex-M3 中断优先级 ---------- */
#ifdef __NVIC_PRIO_BITS

#endif /* FREERTOS_CONFIG_H */
```

## 11. 排错清单

### 11.1 编译或链接失败

- [ ] `FreeRTOSConfig.h` 是否位于 Include Path？
- [ ] 宏名是否与当前 FreeRTOS 版本一致？
- [ ] 是否缺少必要的 `INCLUDE_xxx`？
- [ ] `heap_x.c` 是否恰好加入一个，而不是一个都没有或重复加入？
- [ ] SVC、PendSV、SysTick 处理函数是否缺失或重复定义？
- [ ] 开启 Hook 后是否实现了对应函数？

### 11.2 延时明显不准

- [ ] CubeMX 中最终 HCLK 是多少？
- [ ] `SystemCoreClock` 是否在切换时钟后更新？
- [ ] `configCPU_CLOCK_HZ` 是否与移植层实际 Tick 时钟一致？
- [ ] 是否把 `vTaskDelay(毫秒)` 错当成毫秒，而没有使用 `pdMS_TO_TICKS()`？
- [ ] HAL Tick 与 FreeRTOS Tick 是否使用同一 SysTick 并发生配置冲突？

### 11.3 启动调度器后 HardFault 或断言

- [ ] 中断优先级数字方向是否理解反了？
- [ ] 调用 `...FromISR()` 的中断是否位于允许的优先级范围？
- [ ] NVIC Priority Group 是否被其他初始化代码改写？
- [ ] 任务栈是否过小？是否有大数组或 `printf()` 放在任务局部变量中？
- [ ] FreeRTOS 堆是否不足？
- [ ] ISR 是否误用了普通任务 API？

### 11.4 系统能运行但偶尔卡死

- [ ] 高优先级任务是否一直运行而从不阻塞？
- [ ] 是否在 ISR、Tick Hook 或 Timer Callback 中执行阻塞操作？
- [ ] 队列是否满、定时器命令队列是否太短？
- [ ] 互斥锁是否存在未释放、嵌套顺序错误或死锁？
- [ ] 是否检查过任务栈高水位和最小历史剩余堆？
- [ ] 应用层 Tick 比较是否考虑了无符号回绕？

## 最后记住这张关系图

```text
FreeRTOSConfig.h
├─ CPU_CLOCK_HZ：CPU/Core 实际多快
├─ TICK_RATE_HZ：系统时间粒度
├─ TickType_t：时间计数范围与回绕
├─ PREEMPTION / PRIORITIES：谁先运行
├─ HEAP / STACK：对象和任务放在哪里
├─ MUTEX / NOTIFICATION / TIMER：开放哪些能力
├─ MAX_SYSCALL_INTERRUPT_PRIORITY：中断调用内核的边界
└─ ASSERT / Hook：怎样尽早发现错误
```

读懂这些关系后，`FreeRTOSConfig.h` 就不再是一堆孤立宏，而是一份完整的系统运行规则。
