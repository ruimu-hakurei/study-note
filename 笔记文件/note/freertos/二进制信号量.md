**二进制信号量（Binary Semaphore）** 是 FreeRTOS 里非常重要的同步工具，尤其常见于：

- 中断通知任务
- 任务之间做“事件提醒”
- 等待某件事发生
- 让任务在没事时进入 Blocked，而不是一直空转

你可以先把它理解成一个只有两种状态的“小旗子”：

```
0：没有信号
1：有信号
```

也可以理解成：

> **一个最多只能存 1 个“令牌”的容器。**

---

## 1. 为什么叫“二进制”信号量

因为它只有两种状态：

```
0
1
```

不像计数信号量那样可以：

```
0
1
2
3
4
...
```

所以 Binary Semaphore：

```
空
或
有一个 token
```

比如：

```
Semaphore = 0
```

表示：

> 事件还没发生。

如果某个任务或中断：

```
xSemaphoreGive(...)
```

那么：

```
Semaphore = 1
```

表示：

> 事件发生了。

另一个任务：

```
xSemaphoreTake(...)
```

拿走以后：

```
Semaphore = 0
```

---

# 2. 最直观的模型：门票

你可以把二进制信号量理解成只有一张门票。

```
盒子里没票
Semaphore = 0
```

有人：

```
xSemaphoreGive()
```

相当于：

```
放一张票进去
```

于是：

```
Semaphore = 1
```

任务：

```
xSemaphoreTake()
```

相当于：

```
把票拿走
```

然后：

```
Semaphore = 0
```

---

# 3. 最典型场景：中断通知任务

这是二进制信号量最经典的用途之一。

比如你有一个按键中断：

```
按键按下
   ↓
EXTI中断
   ↓
给二进制信号量
   ↓
任务被唤醒
   ↓
执行处理
```

这种结构比：

```
while (1)
{
    if (button_pressed)
    {
        ...
    }
}
```

好很多。

因为后者一直轮询，浪费 CPU。

---

# 4. 一个完整例子

先创建：

```
SemaphoreHandle_t xButtonSemaphore;
```

然后：

```
xButtonSemaphore = xSemaphoreCreateBinary();
```

任务：

```
void vButtonTask(void *pvParameters)
{
    while (1)
    {
        xSemaphoreTake(
            xButtonSemaphore,
            portMAX_DELAY
        );

        // 按键事件发生
        HandleButton();
    }
}
```

中断里：

```
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    xSemaphoreGiveFromISR(
        xButtonSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(
        xHigherPriorityTaskWoken
    );
}
```

整个流程：

```
ButtonTask
↓
Take不到
↓
Blocked
↓
CPU去做别的事


按键中断发生
↓
GiveFromISR
↓
Semaphore变为1
↓
ButtonTask
Blocked → Ready
↓
调度器选择
↓
ButtonTask运行
↓
Take成功
↓
Semaphore重新变0
↓
执行HandleButton()
```

这个模式以后你会频繁用。

---

# 5. `xSemaphoreCreateBinary()`

创建二进制信号量：

```
SemaphoreHandle_t xSem;

xSem = xSemaphoreCreateBinary();
```

创建成功：

```
xSem != NULL
```

失败：

```
xSem == NULL
```

所以建议：

```
if (xSem == NULL)
{
    Error_Handler();
}
```

因为动态创建需要 FreeRTOS Heap。

---

# 6. 新创建后二进制信号量是什么状态？

现代常用：

```
xSemaphoreCreateBinary()
```

创建出来后通常是：

```
空
Semaphore = 0
```

所以：

```
xSemaphoreTake(xSem, 0);
```

一开始通常拿不到。

必须先有人：

```
xSemaphoreGive(xSem);
```

变成：

```
1
```

才能 Take。

这一点要记住。

---

# 7. `xSemaphoreGive()`

任务上下文中释放/发送信号：

```
xSemaphoreGive(xSem);
```

大概含义：

> “事件发生了，放一个 token。”

如果原来：

```
0
```

那么：

```
0 → 1
```

如果已经：

```
1
```

又 Give：

```
1 → 仍然1
```

因为二进制信号量最大只能保存一个 token。

这点特别重要。

---

# 8. Give 两次会怎么样？

假设：

```
xSemaphoreGive(xSem);
xSemaphoreGive(xSem);
```

你可能以为：

```
有两个信号
```

不是。

二进制信号量最大计数就是：

```
1
```

所以：

```
第一次 Give：
0 → 1

第二次 Give：
1 → 1
```

第二次事件不会被累计成 2。

这也是它和计数信号量最大的区别之一。

---

# 9. `xSemaphoreTake()`

任务想等待信号：

```
xSemaphoreTake(
    xSem,
    xTicksToWait
);
```

它会尝试：

> 拿走 token。

如果：

```
Semaphore = 1
```

那么：

```
Take成功
1 → 0
```

返回：

```
pdTRUE
```

或者成功状态。

---

# 10. 如果 Semaphore = 0 呢？

这时候取决于第二个参数：

```
xTicksToWait
```

例如：

```
xSemaphoreTake(
    xSem,
    0
);
```

意思：

> 不等。

没有信号：

```
立即失败
```

---

如果：

```
xSemaphoreTake(
    xSem,
    pdMS_TO_TICKS(100)
);
```

意思：

> 最多等100ms。

没有 token：

```
Task
Running
↓
Blocked
↓
等待信号或100ms超时
```

---

如果：

```
xSemaphoreTake(
    xSem,
    portMAX_DELAY
);
```

通常表示：

> 一直等，直到信号出现。

所以任务可以长期：

```
Blocked
```

完全不浪费 CPU。

---

# 11. Take 成功和失败怎么判断

例如：

```
if (xSemaphoreTake(
        xSem,
        pdMS_TO_TICKS(100)
    ) == pdTRUE)
{
    // 成功拿到信号
}
else
{
    // 100ms内没有信号
}
```

这个模式非常常见。

---

# 12. 为什么等待信号时 Task 会进入 Blocked

假设：

```
xSemaphoreTake(
    xSem,
    portMAX_DELAY
);
```

而当前：

```
Semaphore = 0
```

那 FreeRTOS 会认为：

> 这个任务现在没法继续干活。

于是：

```
Running
↓
Blocked
```

CPU 去运行别的 Ready Task。

等别人：

```
xSemaphoreGive(...)
```

之后：

```
Blocked
↓
Ready
```

如果这个任务优先级很高，还可能立即抢占当前低优先级任务。

所以二进制信号量和你之前学的任务状态是直接连着的。

---

# 13. 二进制信号量本质上解决什么问题

核心是：

> **同步。**

例如：

```
Task A：
“等数据准备好再运行”

Task B / ISR：
“数据准备好了，通知你”
```

于是：

```
生产者
↓
Give
↓
Binary Semaphore
↓
Take
↓
消费者
```

注意：

> 二进制信号量主要传的是“事件发生了”这个信息，不是复杂数据本身。

---

# 14. 它和 Queue 的区别

Queue：

```
可以真正传数据
```

例如：

```
xQueueSend(xQueue, &imuData, ...);
```

里面保存：

```
imuData
```

而 Binary Semaphore：

```
只表达
“有事发生”
```

没有实际数据负载。

比如：

```
ADC DMA完成
```

只需要告诉 Task：

> 数据好了。

这时候 Binary Semaphore 很适合。

Task醒来以后，自己去读共享 Buffer。

---

# 15. 一个 DMA 场景

例如 ADC DMA：

```
ADC + DMA
↓
buffer填满
↓
DMA完成中断
↓
Give Binary Semaphore
↓
ProcessingTask醒来
↓
处理buffer
```

中断：

```
void HAL_ADC_ConvCpltCallback(ADC_HandleTypeDef *hadc)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    xSemaphoreGiveFromISR(
        xADCSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(
        xHigherPriorityTaskWoken
    );
}
```

任务：

```
void vADCTask(void *pvParameters)
{
    while (1)
    {
        xSemaphoreTake(
            xADCSemaphore,
            portMAX_DELAY
        );

        ProcessADCBuffer();
    }
}
```

非常典型。

---

# 16. 为什么 ISR 里必须用 `FromISR`

任务里：

```
xSemaphoreGive()
```

中断里：

```
xSemaphoreGiveFromISR()
```

不能混。

因为 ISR：

```
不能阻塞
不能等待
必须快速退出
```

所以 FreeRTOS 专门提供 ISR 安全版本。

你以后看到：

```
xxxFromISR
```

就应该立刻想到：

> 中断专用 API。

---

# 17. `xHigherPriorityTaskWoken` 到底干什么

这是很多初学者第一次看最迷惑的地方：

```
BaseType_t xHigherPriorityTaskWoken = pdFALSE;
```

然后：

```
xSemaphoreGiveFromISR(
    xSemaphore,
    &xHigherPriorityTaskWoken
);
```

什么意思？

假设：

```
Task A priority = 1
当前正在运行

Task B priority = 4
正在Blocked等Semaphore
```

中断发生：

```
ISR
↓
Give Semaphore
↓
Task B
Blocked → Ready
```

因为：

```
Task B priority 4
>
Task A priority 1
```

那么：

```
xHigherPriorityTaskWoken = pdTRUE
```

表示：

> 这次中断唤醒了一个比当前任务优先级更高的任务。

于是：

```
portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
```

告诉系统：

> 中断退出以后赶紧切换任务。

所以：

```
Task A
↓
ISR
↓
唤醒 Task B
↓
ISR退出
↓
直接运行Task B
```

这就是实时响应。

---

# 18. 为什么二进制信号量不能保存多次事件

这是它非常重要的限制。

假设：

```
Task还没来得及Take
```

中断连续发生：

```
事件1
事件2
事件3
```

Binary Semaphore：

```
第一次：
0 → 1

第二次：
仍然1

第三次：
仍然1
```

最后 Task：

```
xSemaphoreTake()
```

只知道：

> 至少发生过一次。

它不知道：

```
到底发生了1次
还是3次
```

所以如果你需要记录次数，就应该考虑：

> **Counting Semaphore，计数信号量。**

---

# 19. 二进制信号量和计数信号量区别

### Binary

```
0 / 1
```

适合：

```
事件是否发生
```

例如：

```
DMA完成
按键按下
数据准备完成
```

---

### Counting

```
0 ~ N
```

适合：

```
事件发生了多少次
资源还有多少个
```

例如：

```
收到3个数据包
↓
count = 3
```

Task 每 Take 一次：

```
3 → 2 → 1 → 0
```

---

# 20. 二进制信号量和 Mutex 也不要混

这是 FreeRTOS 初学最重要的区分之一。

它们底层都和 Queue 有关系，但用途不同。

### Binary Semaphore

主要用于：

> **同步、通知。**

典型：

```
ISR
↓
Give
↓
Task
```

---

### Mutex

主要用于：

> **保护共享资源。**

典型：

```
Task A
Task B
   ↓
共享UART
   ↓
Mutex保护
```

---

# 21. 为什么 Mutex 不能简单用 Binary Semaphore 代替

最关键差别之一：

> Mutex 有优先级继承，Binary Semaphore 没有。

假设：

```
LowTask priority = 1
HighTask priority = 5
```

LowTask 拿着资源。

HighTask也要资源。

Mutex 可以通过：

```
Priority Inheritance
```

临时提高 LowTask 优先级，减少优先级反转问题。

Binary Semaphore 没这个机制。

所以：

```
资源互斥
→ Mutex

事件同步
→ Binary Semaphore
```

这是非常重要的工程规则。

---

# 22. Binary Semaphore 可以谁 Give、谁 Take？

不像 Mutex 那样强调“谁拿谁还”。

Binary Semaphore 可以：

```
Task A Give
Task B Take
```

也可以：

```
ISR Give
Task Take
```

甚至：

```
Task A Give
Task B Give
Task C Take
```

它更像事件 token。

而 Mutex：

> 通常谁 Take，谁应该 Give。

因为它有“所有者”概念。

---

# 23. 二进制信号量底层为什么和 Queue 有关

FreeRTOS 里 Semaphore 大量复用 Queue 机制。

你可以把 Binary Semaphore 想成：

```
长度 = 1
数据大小 = 0
```

的特殊 Queue。

普通 Queue：

```
┌────┬────┬────┐
│数据│数据│数据│
└────┴────┴────┘
```

Binary Semaphore：

```
┌────┐
│token│
└────┘
```

我们不关心 token 是什么。

只关心：

```
有 / 没有
```

所以：

```
Give
```

类似往 Queue 塞一个“占位符”。

```
Take
```

类似取走。

---

# 24. 为什么 `semphr.h` 没有对应的 `semphr.c`

你前面源码结构里看过：

```
semphr.h
```

但是没有：

```
semphr.c
```

原因就是：

> Semaphore 的核心实现大量在 `queue.c`。

所以：

```
semphr.h
↓
宏 / API封装
↓
queue.c
```

这就是你现在学 Binary Semaphore 后，源码结构真正能串起来的地方。

# 25. 一个 Task-to-Task 例子

假设：

```
SensorTask
↓
采集完成
↓
给Semaphore
↓
ControlTask醒来
```

创建：

```
SemaphoreHandle_t xDataReadySem;
```

初始化：

```
xDataReadySem = xSemaphoreCreateBinary();

if (xDataReadySem == NULL)
{
    Error_Handler();
}
```

Sensor：

```
void vSensorTask(void *pvParameters)
{
    while (1)
    {
        ReadSensor();

        xSemaphoreGive(xDataReadySem);

        vTaskDelay(pdMS_TO_TICKS(10));
    }
}
```

Control：

```
void vControlTask(void *pvParameters)
{
    while (1)
    {
        xSemaphoreTake(
            xDataReadySem,
            portMAX_DELAY
        );

        Control();
    }
}
```

流程：

```
ControlTask
↓
Blocked

SensorTask采集完成
↓
Give
↓
ControlTask Ready
↓
如果优先级高
立即抢占
↓
Control()
```

---

# 26. 如果两个 Task 都在等同一个 Binary Semaphore

例如：

```
Task A
Task B
```

都：

```
xSemaphoreTake(xSem, portMAX_DELAY);
```

现在只有一次：

```
xSemaphoreGive(xSem);
```

那么通常：

> 只会有一个等待任务成功获得这个 token。

FreeRTOS 会根据优先级等规则选择等待者。

如果：

```
TaskA priority = 3
TaskB priority = 1
```

通常高优先级 TaskA 更有机会先获得。

所以二进制信号量不是广播机制。

---

# 27. 如果我想一次唤醒很多任务怎么办？

Binary Semaphore 不适合“广播”。

如果你想：

```
一个事件
↓
Task A知道
Task B也知道
Task C也知道
```

更适合考虑：

```
Event Group
```

或者其它广播式设计。

因为 Binary Semaphore 一个 token 通常只会被一个 Task 消耗掉。

---

# 28. Give 后如果没人等待会怎么样

假设：

```
Semaphore = 0
```

然后：

```
xSemaphoreGive(xSem);
```

变成：

```
1
```

现在没有 Task 在等待。

没关系。

这个 token 会留在那里。

以后某个 Task：

```
xSemaphoreTake(xSem, 0);
```

会立即成功：

```
1 → 0
```

所以 Binary Semaphore 有一点“记忆”：

> 至少能记住一次事件。

但只能记住一次。

---

# 29. 这和 Task Notification 有什么关系

你以后会发现：

```
ISR → Binary Semaphore → Task
```

很多场景可以用：

```
ISR → Task Notification → Task
```

代替。

Task Notification 通常：

```
更轻量
更快
内存开销更小
```

所以现代 FreeRTOS 工程里，如果：

> 一个事件只通知一个固定 Task

Task Notification 往往很合适。

但是 Binary Semaphore：

```
概念更通用
多个Task都可以等待
教学和工程都很常见
```

所以必须学懂。

---

# 30. 一个非常重要的错误：ISR 里用普通 Give

错误：

```
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    xSemaphoreGive(xSem);
}
```

不要这样。

应该：

```
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    xSemaphoreGiveFromISR(
        xSem,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(
        xHigherPriorityTaskWoken
    );
}
```

只要在 ISR 里，就优先想：

```
FromISR
```

---

# 31. 另一个错误：拿 Binary Semaphore 当锁

例如：

```
xSemaphoreTake(xBinarySem, portMAX_DELAY);

UART_Send();

xSemaphoreGive(xBinarySem);
```

技术上某些简单情况下能工作。

但如果你真正是在：

> 保护 UART 共享资源

应该：

```
xSemaphoreCreateMutex()
```

而不是 Binary Semaphore。

因为 Mutex 的设计语义和优先级继承更符合互斥保护。

# 32. Binary Semaphore 的典型使用场景

你以后机器人/STM32 项目里特别常见：

```
DMA完成
↓
Task处理数据
```

```
ADC转换完成
↓
Signal Processing Task
```

```
按键中断
↓
Button Task
```

```
传感器 DRDY 中断
↓
IMU Task
```

```
通信接收完成
↓
Protocol Task
```

这些都是：

> 事件发生 → 唤醒任务

非常适合 Binary Semaphore。

## 最后把二进制信号量压缩成一张图

```
                   Binary Semaphore

                     0 / 1
                       │
          ┌────────────┴────────────┐
          │                         │

       Give                      Take
          │                         │
        0 → 1                     1 → 0
          │                         │
      产生事件                  消费事件
```

如果 Take 时：

```
Semaphore = 0
```

并允许等待：

```
Task
Running
↓
Blocked
```

别人 Give：

```
Semaphore
0 → 1
↓
Task
Blocked → Ready
```

Task 得到 CPU：

```
Take
1 → 0
↓
处理事件
```

你可以记成一句最核心的话：

> **二进制信号量不是用来“传数据”的，而是用来告诉任务：“某件事发生了，你现在可以继续干活了。”**

然后再记两个工程规则：

```
中断通知Task
→ Binary Semaphore / Task Notification
```

```
保护共享资源
→ Mutex
```

这两个分清以后，后面学计数信号量和互斥锁就会非常顺。
