## 1. 任务到底是什么

任务（Task）可以理解为一个由 FreeRTOS 调度的独立执行单元。它通常由一个永不返回的 C 函数实现：

```c
void LedTask(void *argument)
{
    for (;;)
    {
        ToggleLed();
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

普通函数由调用者决定何时执行和返回；任务则由调度器决定何时获得 CPU：

```text
普通函数：调用 → 执行 → 返回

FreeRTOS 任务：
创建 → Ready → 被调度为 Running
              ↓
        阻塞/抢占/挂起
              ↓
        保存现场，稍后继续
```

### 单核 STM32 并不是真的同时执行多个任务

STM32F103 是单核 MCU，同一时刻最多只有一个任务处于 Running。多任务效果来自快速上下文切换：

```text
0 ms       1 ms       2 ms       3 ms
Task A ────┐           ┌─────────
           └─ Task B ──┘
```

切换足够快时，人会感觉任务同时运行，但 CPU 每个瞬间仍只执行一条指令流。

> [!note] 中断不是任务
> ISR 会暂时打断正在运行的任务。中断结束后，CPU 可能返回原任务，也可能因为 ISR 唤醒了更高优先级任务而切换到另一任务。

### 一个任务应该负责什么

推荐按“职责与触发条件”拆分，而不是每个函数都建成任务：

| 适合独立成任务 | 更适合普通函数 |
|---|---|
| 有独立周期，如 10 ms 控制环 | 只被一个任务调用的计算步骤 |
| 长期等待一个事件，如串口数据 | 很短、无独立生命周期的驱动封装 |
| 有明确时限和优先级 | 必须与调用者同步完成的操作 |
| 需要阻塞等待队列、通知或信号量 | 仅为了“代码看起来模块化” |

任务并非越多越好。每个任务都需要 TCB、栈和调度管理成本。

## 2. TCB、任务栈与上下文

FreeRTOS 管理的不是任务函数名字，而是任务对应的数据结构和执行现场。

### 2.1 TCB：任务控制块

TCB（Task Control Block）保存内核管理任务所需的信息，概念上包括：

```text
TCB
├─ 任务栈指针
├─ 当前/基础优先级
├─ 任务状态和列表节点
├─ 任务名称
├─ 任务通知值
└─ 其他端口或配置相关信息
```

不要依赖 TCB 的具体字段布局。它是内核内部实现，可能随 FreeRTOS 版本和配置改变。

### 2.2 每个任务都有自己的栈

任务栈用于保存：

- 局部变量；
- 函数调用返回地址；
- 保存的 CPU 寄存器；
- 上下文切换现场；
- 某些库函数使用的临时数据。

```text
Task A → TCB A + Stack A
Task B → TCB B + Stack B
Task C → TCB C + Stack C
```

任务被切出时，内核保存它的寄存器和栈位置；再次运行时恢复现场，所以任务会从上次停下的位置继续，而不是从函数开头重新执行。

### 2.3 为什么创建任务会消耗 Heap

动态创建任务时，`xTaskCreate()` 通常要从 FreeRTOS Heap 中分配：

```text
任务的 TCB + 任务栈
```

静态创建 `xTaskCreateStatic()` 则由应用提供 TCB 和栈缓冲区。详见 [[配置文件#5. 内存与栈配置]]。

> [!warning] 栈深度通常不是字节
> `xTaskCreate()` 的栈深度参数单位是 `StackType_t`。Cortex-M3 中一个 `StackType_t` 常为 4 字节，因此深度 256 常约等于 1024 字节，但必须以当前端口定义为准。

## 3. 创建任务：`xTaskCreate()`

### 3.1 函数原型

```c
BaseType_t xTaskCreate(
    TaskFunction_t task_entry,          // 任务入口函数
    const char * const task_name,       // 调试用名称
    configSTACK_DEPTH_TYPE stack_depth, // 栈深度，通常以 StackType_t 为单位
    void *parameter,                    // 传给任务的参数
    UBaseType_t priority,               // 初始优先级
    TaskHandle_t *created_task          // 输出任务句柄，可为 NULL
);
```

典型调用：

```c
TaskHandle_t sensor_task_handle = NULL;

BaseType_t result = xTaskCreate(
    SensorTask,               // 入口函数
    "Sensor",                // 调试器中显示的名字
    256,                      // Cortex-M3 中常约为 1 KB，需实测高水位
    NULL,                     // 本例不传参数
    3,                        // FreeRTOS 数字越大，任务优先级越高
    &sensor_task_handle       // 保存句柄，以便以后通知或查询该任务
);

configASSERT(result == pdPASS);
```

失败通常意味着 FreeRTOS Heap 无法提供 TCB 和任务栈。

### 3.2 任务函数不能直接返回

```c
void BadTask(void *argument)
{
    DoSomething();
} // 错误：任务函数不应直接 return
```

正确方式是永久循环，或在不再需要时删除自己：

```c
void OneShotTask(void *argument)
{
    PerformStartupCalibration();

    vTaskDelete(NULL); // NULL 表示删除当前任务；函数不会再继续
}
```

### 3.3 参数怎样传给任务

`parameter` 只是一个指针，不会自动复制指向的数据：

```c
typedef struct
{
    GPIO_TypeDef *port;
    uint16_t pin;
    TickType_t period;
} LedTaskConfig;

static LedTaskConfig green_led = {
    .port = GPIOC,
    .pin = GPIO_PIN_13,
    .period = pdMS_TO_TICKS(500)
};

void LedTask(void *argument)
{
    const LedTaskConfig *config = (const LedTaskConfig *)argument;

    for (;;)
    {
        HAL_GPIO_TogglePin(config->port, config->pin);
        vTaskDelay(config->period);
    }
}

/* green_led 必须在任务整个生命周期内保持有效，因此使用 static。 */
xTaskCreate(LedTask, "GreenLED", 128, &green_led, 1, NULL);
```

不要传入创建函数内的普通局部变量地址，因为创建函数返回后，该地址对应的栈空间会失效。

### 3.4 任务创建后何时运行

#### 调度器尚未启动

`xTaskCreate()` 只把任务放入 Ready List。调用 `vTaskStartScheduler()` 后，最高优先级 Ready 任务首先运行。

#### 调度器已经运行

若新建任务优先级高于当前任务，它可能在 `xTaskCreate()` 内部触发调度，先运行新任务，然后创建者才从 API 返回。

> [!important] 不要依赖“创建顺序就是执行顺序”
> 执行顺序由任务状态和优先级决定，不由代码里先调用哪次 `xTaskCreate()` 决定。

### 3.5 Task Handle：任务句柄

`TaskHandle_t` 是应用引用某个任务的安全入口，可用于：

- 向指定任务发送通知；
- 挂起、恢复或删除指定任务；
- 修改或查询优先级；
- 获取任务状态信息。

常见 `NULL` 含义依 API 而定：

```c
vTaskDelete(NULL);            // 当前任务
vTaskPrioritySet(NULL, 3);    // 当前任务
uxTaskPriorityGet(NULL);      // 当前任务
```

不能把所有 API 中的 `NULL` 都机械理解成“当前任务”，必须查看该 API 的参数说明。

## 4. 四种任务状态与状态转换

### 4.1 状态总表

| 状态 | 含义 | 是否占用 CPU | 怎样离开 |
|---|---|---:|---|
| Running | 当前正在执行 | 是 | 被抢占、阻塞、挂起、删除 |
| Ready | 可以执行，但 CPU 正给其他任务 | 否 | 被调度器选中 |
| Blocked | 等待时间或事件 | 否 | 超时或等待的事件发生 |
| Suspended | 被显式挂起 | 否 | 被显式恢复 |

单核 STM32 同一时刻只有一个任务 Running，但可以有很多 Ready、Blocked 和 Suspended 任务。

### 4.2 状态转换图

```text
                   时间到/事件发生
            ┌────────────────────────┐
            │                        ▼
Running ──阻塞 API──> Blocked ─────> Ready
   ▲                                  │
   │                                  │ 调度器选择
   └──────────────────────────────────┘
             被抢占/时间片结束

Running/Ready/Blocked ──vTaskSuspend──> Suspended
Suspended ──────────────vTaskResume───> Ready

任意可删除状态 ──vTaskDelete──> 等待 Idle Task 回收内核资源
```

### 4.3 Running：正在执行

Running 任务正在使用 CPU。若它调用普通函数，该函数仍属于该任务的执行上下文，并不会自动产生一个新任务。

Running 常见去向：

- 被更高优先级 Ready 任务抢占 → Ready；
- 同优先级时间片轮转 → Ready；
- 调用延时或等待 API → Blocked；
- 调用 `vTaskSuspend()` → Suspended；
- 调用 `vTaskDelete()` → 删除。

### 4.4 Ready：能运行但暂时没轮到

Ready 任务不等待任何条件，只是当前有相同或更高优先级任务占用 CPU。

```text
Task A：优先级 3，Running
Task B：优先级 2，Ready
Task C：优先级 1，Ready
```

只有 Task A 阻塞、挂起、删除或被更高优先级任务替代后，调度器才重新选择。

### 4.5 Blocked：主动等待而不消耗 CPU

任务可以等待：

- 时间：`vTaskDelay()`、`xTaskDelayUntil()`；
- 队列数据：`xQueueReceive()`；
- 信号量：`xSemaphoreTake()`；
- 任务通知：`ulTaskNotifyTake()`、`xTaskNotifyWait()`；
- 事件组、流缓冲区、消息缓冲区等。

```c
/* 队列为空时，任务最多阻塞 100 ms，不会空转查询。 */
if (xQueueReceive(data_queue, &data, pdMS_TO_TICKS(100)) == pdPASS)
{
    Process(data);
}
```

Blocked 是 RTOS 高效运行的关键。没有工作就阻塞，CPU 才能运行其他任务或进入 Idle/低功耗。

### 4.6 Suspended：人为冻结

```c
vTaskSuspend(worker_handle);
vTaskResume(worker_handle);
```

Suspended 没有超时时间，也不会因为队列数据、信号量或 Tick 自动恢复，只能由显式恢复操作改变。

### 4.7 Blocked 与 Suspended 的区别

| 对比项 | Blocked | Suspended |
|---|---|---|
| 原因 | 等待时间或事件 | 被人为冻结 |
| 能否自动恢复 | 可以 | 不可以 |
| 是否适合正常任务同步 | 是 | 通常不是首选 |
| 常用方法 | 队列、通知、信号量、延时 | `vTaskSuspend/Resume` |

若需求是“数据到了就工作”，应该阻塞等待数据，而不是让另一个任务负责 Resume。Suspend/Resume 容易形成隐式控制关系，也可能产生恢复时机竞争。

### 4.8 删除是不是第五种状态

从调度模型看，常用核心状态仍是四种。某些诊断 API 会返回 `eDeleted`，表示任务已删除但其内核资源可能还等待 Idle Task 回收，它更像生命周期结束标记。

## 5. 调度器怎样选择任务

### 5.1 最基本原则

```text
永远选择当前 Ready 任务中优先级最高的一个运行
```

FreeRTOS **任务优先级数字越大越高**：

```text
Priority 4 > Priority 3 > Priority 2 > Priority 1 > Priority 0
```

这与 Cortex-M NVIC 的“数字越小，中断越紧急”方向相反。

### 5.2 抢占式调度

配置：

```c
#define configUSE_PREEMPTION 1
```

若高优先级任务由 Blocked 变为 Ready，调度器可以立即暂停当前低优先级任务：

```text
日志任务 P1 正在运行
        ↓
控制任务 P4 等待的通知到达
        ↓
控制任务 P4 变为 Ready 并抢占日志任务
```

被抢占任务的上下文保存在自己的栈和 TCB 中，以后从原位置继续。

### 5.3 同优先级时间片

配置：

```c
#define configUSE_TIME_SLICING 1
```

多个相同最高优先级任务同时 Ready 时，可以随 Tick 轮流运行。时间片主要解决“相同优先级”，抢占主要解决“不同优先级”，不要混为一谈。

### 5.4 协作式调度

```c
#define configUSE_PREEMPTION 0
```

当前任务需要主动阻塞或让出 CPU，其他任务才有机会运行。若一个协作式任务永不阻塞也不 Yield，其他任务可能被饿死。

协作式不等于没有中断；硬件中断仍可以发生，只是任务级切换规则不同。

### 5.5 `taskYIELD()` 能做什么

在常见抢占式配置中，`taskYIELD()` 主要让同优先级 Ready 任务获得运行机会，不能把它当成“保证低优先级任务运行”的 API。

```c
for (;;)
{
    DoTinyWork();
    taskYIELD();
}
```

上面的任务仍保持 Ready，可能持续占住所有低优先级任务。若暂时没有工作，应进入 Blocked：

```c
ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
```

### 5.6 优先级设计原则

优先级表达的是**响应时限**，不是模块的重要程度或代码量。

| 任务类型 | 常见相对优先级 | 原因 |
|---|---:|---|
| 快速安全控制 | 高 | 有严格截止时间，单次执行必须短 |
| 数据采集/协议接收 | 中高 | 需要及时取走硬件或缓冲数据 |
| UI、状态机 | 中 | 有响应要求但通常不需抢占控制环 |
| 日志、存储 | 低 | 可延后，不应影响实时控制 |

> [!danger] 最高优先级任务永不阻塞
> 如果它一直处于 Ready，所有低优先级任务都可能永远无法运行，Idle Task 也不能回收已删除任务的资源。

任务越高优先级，越要做到：

1. 单次执行时间短；
2. 完成后立即阻塞；
3. 不做慢速日志和长时间轮询；
4. 不长期持有共享资源。

## 6. 延时与周期任务

### 6.1 `vTaskDelay()`：相对延时

```c
vTaskDelay(pdMS_TO_TICKS(100));
```

从调用 API 的时刻开始阻塞 100 ms。若任务本轮处理耗时 7 ms，则两次开始执行的间隔大约是：

```text
7 ms 工作 + 100 ms 延时 = 107 ms
```

适合：LED 闪烁、退避等待、对严格周期没有要求的任务。

### 6.2 `xTaskDelayUntil()`：固定周期

现代 FreeRTOS 文档使用：

```c
void ControlTask(void *argument)
{
    TickType_t last_wake = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(10);

    for (;;)
    {
        RunControlStep();

        /* 下一次唤醒时间基于固定时间轴，不基于本轮函数结束时刻。 */
        BaseType_t delayed = xTaskDelayUntil(&last_wake, period);

        if (delayed == pdFALSE)
        {
            /* 预定唤醒时间已经过去：本轮可能超时，应记录而不是在此打印。 */
            control_deadline_miss++;
        }
    }
}
```

旧版本或旧教程常见 `vTaskDelayUntil()`。两者名称/返回值存在版本差异，应以当前工程的 `task.h` 为准。

适合：电机控制、传感器固定采样、周期通信。

### 6.3 时间到了不等于马上运行

任务延时到期后只是从 Blocked 变为 Ready。如果此时有更高优先级任务运行，它仍要等待：

```text
延时到期 → Ready → 等待 CPU → Running
```

因此周期精度还受到：

- 更高优先级任务最长执行时间；
- 中断延迟和中断执行时间；
- 临界区长度；
- 系统 Tick 分辨率。

### 6.4 不要用忙等待代替阻塞

```c
// 错误：任务一直占用 CPU 查询时间
while ((xTaskGetTickCount() - start) < pdMS_TO_TICKS(100))
{
}
```

```c
// 正确：让任务进入 Blocked，CPU 可运行其他任务
vTaskDelay(pdMS_TO_TICKS(100));
```

## 7. 挂起、恢复、改优先级和删除

### 7.1 挂起与恢复

```c
vTaskSuspend(task_handle);       // 任务上下文调用
vTaskResume(task_handle);
```

ISR 中若确实需要恢复任务，应使用当前版本提供的 ISR 安全 API，例如 `xTaskResumeFromISR()`，并遵守 FreeRTOS 中断优先级边界。

正常事件同步优先考虑任务通知、队列或信号量。

### 7.2 修改优先级

```c
vTaskPrioritySet(worker_handle, 3);
UBaseType_t priority = uxTaskPriorityGet(worker_handle);
```

改变优先级可能立即触发调度。动态调优先级适合少数明确状态切换，不适合用来掩盖错误架构。频繁调整会让系统时序更难推理。

### 7.3 删除任务

```c
vTaskDelete(worker_handle); // 删除指定任务
vTaskDelete(NULL);          // 删除当前任务
```

对 `xTaskCreate()` 动态创建的任务，内核分配的 TCB 和栈通常由 Idle Task 完成最终回收，因此必须让 Idle Task 获得运行机会。

`vTaskDelete()` 不会自动释放任务自己申请或占用的资源，例如：

- `pvPortMalloc()` 或 C 库分配的业务缓冲区；
- 已打开的文件、外设或 DMA；
- 当前持有的互斥锁；
- 应用层登记表中的对象。

推荐让任务自行清理后删除自己：

```c
void TemporaryTask(void *argument)
{
    uint8_t *buffer = pvPortMalloc(256);

    if (buffer != NULL)
    {
        DoTemporaryWork(buffer);
        vPortFree(buffer);       // 先释放业务资源
    }

    vTaskDelete(NULL);           // 再结束任务
}
```

长期运行的嵌入式系统通常创建固定任务并通过 Blocked 管理工作，比频繁创建/删除任务更容易验证内存和时序。

## 8. FreeRTOS 内部怎样管理任务

理解列表能解释“任务状态为什么切换得很快”。概念上，内核会维护：

```text
Ready Lists：按优先级组织可运行任务
Delayed Lists：按唤醒 Tick 组织延时任务
Overflow Delayed List：处理 Tick 回绕后的唤醒时间
Event Lists：等待队列、信号量等事件的任务
Suspended List：显式挂起的任务
Termination List：已删除、等待 Idle Task 回收的任务
```

### 8.1 为什么每个优先级有 Ready List

调度器首先快速找到最高的非空优先级，再从该 Ready List 选择任务：

```text
Priority 4 Ready List: [ControlTask]
Priority 3 Ready List: [SensorTask, CommTask]
Priority 2 Ready List: []
Priority 1 Ready List: [LogTask]
Priority 0 Ready List: [IdleTask]
```

### 8.2 `vTaskDelay()` 内部发生了什么

概念过程：

```text
当前任务从 Ready List 移除
        ↓
计算 wake_tick = current_tick + delay
        ↓
插入 Delayed List
        ↓
触发一次调度
        ↓
Tick 到期后移回 Ready List
```

### 8.3 为什么没有单独的 Running List

Running 任务本质上就是当前被调度器选中的 Ready 任务。内核通过“当前任务指针”记录它，不需要再维护一条只有一个节点的列表。

> [!note] 这是帮助理解的抽象
> 列表名称、字段和具体算法属于内核实现，调试时可以观察，但应用代码不要直接操作内核列表。

## 9. 系统任务：Idle Task 与 Timer Task

### 9.1 Idle Task

启动调度器时内核自动创建 Idle Task，优先级为 0。当没有其他 Ready 任务时运行。

主要作用包括：

- 保证始终有任务可运行；
- 回收部分已删除动态任务的 TCB 和栈；
- 可配合 Idle Hook 或 Tickless Idle 进入低功耗。

若任何高优先级任务一直不阻塞，Idle Task 可能无法运行，资源回收和低功耗都会受影响。

### 9.2 Timer Service Task

启用软件定时器后，内核会创建 Timer Service Task：

```c
#define configUSE_TIMERS             1
#define configTIMER_TASK_PRIORITY    2
#define configTIMER_QUEUE_LENGTH     10
```

所有软件定时器 Callback 共用该任务上下文。Callback 过长或阻塞会延误其他定时器，因此复杂工作应通过队列/通知交给业务任务。

## 10. 栈、堆与运行状态诊断

### 10.1 栈高水位

```c
UBaseType_t minimum_free_words = uxTaskGetStackHighWaterMark(task_handle);
```

它表示任务运行以来最紧张时仍未使用的栈量，单位通常为 `StackType_t`，不是字节。

诊断思路：

```text
值很大 → 栈可能配置过多，可谨慎缩减
值很小 → 接近栈溢出，应增加栈并检查大局部变量/深调用
值为 0 → 高风险，立即排查
```

不要只在系统空闲时测一次；应覆盖通信峰值、错误处理和最长调用链。

### 10.2 FreeRTOS Heap

```c
size_t free_now = xPortGetFreeHeapSize();
size_t minimum_ever_free = xPortGetMinimumEverFreeHeapSize();
```

`minimum_ever_free` 更能反映历史内存峰值。若 `xTaskCreate()` 返回失败，应同时检查：

- `configTOTAL_HEAP_SIZE`；
- 任务栈深度是否过大；
- 队列等对象是否占用大量内存；
- 是否存在反复创建但未正确回收的对象。

### 10.3 查询任务状态

根据配置和版本，可使用：

```c
eTaskState state = eTaskGetState(task_handle);
UBaseType_t priority = uxTaskPriorityGet(task_handle);
TickType_t now = xTaskGetTickCount();
```

`vTaskList()`、运行时间统计等调试功能会增加代码和运行开销，需要对应配置宏。不要在高频任务或 ISR 中反复格式化输出任务列表。

## 11. 项目实例一：双 LED 周期任务

### 11.1 目标

- LED A 每 200 ms 翻转一次；
- LED B 每 1000 ms 翻转一次；
- 两个任务同优先级；
- 用 Blocked 代替忙等待。

### 11.2 完整示例

```c
#include "FreeRTOS.h"
#include "task.h"
#include "main.h"

typedef struct
{
    GPIO_TypeDef *port;
    uint16_t pin;
    TickType_t period;
} LedConfig;

static const LedConfig led_fast = {
    .port = GPIOA,
    .pin = GPIO_PIN_0,
    .period = pdMS_TO_TICKS(200)
};

static const LedConfig led_slow = {
    .port = GPIOA,
    .pin = GPIO_PIN_1,
    .period = pdMS_TO_TICKS(1000)
};

static void LedTask(void *argument)
{
    const LedConfig *config = (const LedConfig *)argument;

    for (;;)
    {
        HAL_GPIO_TogglePin(config->port, config->pin);

        /* 延时期间任务进入 Blocked，不消耗 CPU。 */
        vTaskDelay(config->period);
    }
}

void AppTasksInit(void)
{
    BaseType_t ok;

    ok = xTaskCreate(LedTask, "LedFast", 128,
                     (void *)&led_fast, 1, NULL);
    configASSERT(ok == pdPASS);

    ok = xTaskCreate(LedTask, "LedSlow", 128,
                     (void *)&led_slow, 1, NULL);
    configASSERT(ok == pdPASS);
}
```

### 11.3 调度过程

```text
t=0        LedFast 运行 → 翻转 → Blocked 200 ms
           LedSlow 运行 → 翻转 → Blocked 1000 ms
           Idle Task 运行

t=200 ms   LedFast 到期 → Ready → Running → 再次 Blocked
t=400 ms   LedFast 重复
...
t=1000 ms  LedFast、LedSlow 都可能 Ready，同优先级按调度规则运行
```

这个项目说明：多任务的关键不是两个任务持续占 CPU，而是绝大多数时间都在 Blocked。

### 11.4 如果删掉延时会怎样

两个任务会不断翻转 GPIO 并一直 Ready。若某个任务优先级更高，它可能让低优先级 LED 永远无法运行；即使同优先级，CPU 也会被无意义循环占满。

## 12. 项目实例二：传感器采集流水线

### 12.1 需求拆分

设计一个温湿度显示系统：

- SensorTask：每 100 ms 固定采样，优先级 3；
- DisplayTask：有新数据才刷新屏幕，优先级 1；
- 只关心最新值，显示慢时允许覆盖旧样本。

```text
SensorTask ──长度为 1 的最新值队列──> DisplayTask
周期唤醒                                阻塞等数据
```

### 12.2 为什么使用长度为 1 的队列

显示系统通常不需要依次显示所有历史样本，只需要最新值。长度为 1 的队列配合 `xQueueOverwrite()` 可以避免数据积压。

如果每个样本都必须保存，例如数据记录仪，就应使用更长队列并设计“队列满”的策略。

### 12.3 示例代码

```c
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

typedef struct
{
    TickType_t tick;
    float temperature;
    float humidity;
    uint8_t valid;
} SensorSample;

static QueueHandle_t latest_sample_queue;
static volatile uint32_t sensor_deadline_miss;

static SensorSample ReadSensorSample(void)
{
    SensorSample sample = {0};

    sample.tick = xTaskGetTickCount();
    sample.valid = Sensor_Read(&sample.temperature, &sample.humidity);
    return sample;
}

static void SensorTask(void *argument)
{
    TickType_t last_wake = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(100);

    (void)argument;

    for (;;)
    {
        SensorSample sample = ReadSensorSample();

        /* 队列长度必须为 1。复制最新结构体，旧数据尚未读取时会被覆盖。 */
        xQueueOverwrite(latest_sample_queue, &sample);

        /* 固定周期比 vTaskDelay(100 ms) 更不容易累计漂移。 */
        if (xTaskDelayUntil(&last_wake, period) == pdFALSE)
        {
            /* 不要在实时任务中 printf；只累计计数，交给低优先级任务读取。 */
            sensor_deadline_miss++;
        }
    }
}

static void DisplayTask(void *argument)
{
    SensorSample sample;
    (void)argument;

    for (;;)
    {
        /* 没有数据时永久 Blocked，不轮询、不占 CPU。 */
        if (xQueueReceive(latest_sample_queue,
                          &sample,
                          portMAX_DELAY) == pdPASS)
        {
            if (sample.valid)
            {
                Display_ShowTemperature(sample.temperature);
                Display_ShowHumidity(sample.humidity);
            }
            else
            {
                Display_ShowSensorError();
            }
        }
    }
}

void SensorProjectInit(void)
{
    latest_sample_queue = xQueueCreate(1, sizeof(SensorSample));
    configASSERT(latest_sample_queue != NULL);

    configASSERT(xTaskCreate(SensorTask, "Sensor", 256,
                             NULL, 3, NULL) == pdPASS);

    configASSERT(xTaskCreate(DisplayTask, "Display", 256,
                             NULL, 1, NULL) == pdPASS);
}
```

### 12.4 一次数据到达时发生什么

```text
SensorTask(P3) 到期，从 Blocked → Ready → Running
        ↓
读取传感器并覆盖队列
        ↓
DisplayTask(P1) 从 Blocked → Ready
        ↓
SensorTask 调用 xTaskDelayUntil() → Blocked
        ↓
DisplayTask 成为最高 Ready 任务 → Running
        ↓
显示完成，再次阻塞在 xQueueReceive()
```

这就是典型的“高优先级生产者快速完成，低优先级消费者有数据才运行”。

### 12.5 可以继续怎样扩展

- 增加 AlarmTask，用任务通知或事件组接收越界事件；
- 增加 LogTask，用较长队列保存每个必须记录的样本；
- 传感器由硬件中断完成时，让 ISR 只通知 SensorTask，不在 ISR 中进行浮点计算或显示。

## 13. 项目实例三：机器人控制系统

这个例子把周期任务、事件任务、中断唤醒和优先级放在一起。

### 13.1 任务架构

| 任务 | 优先级 | 唤醒方式 | 工作内容 |
|---|---:|---|---|
| ControlTask | 4 | IMU 数据通知/急停通知 | 姿态控制、计算电机输出 |
| ImuTask | 3 | 5 ms 固定周期 | 读取 IMU，更新最新姿态数据 |
| CommandTask | 2 | 串口接收队列 | 解析指令，更新控制目标 |
| StatusTask | 1 | 500 ms 周期 | LED、状态上报 |
| LogTask | 1 | 日志队列 | 慢速输出，不影响控制 |
| Idle Task | 0 | 无其他 Ready 任务 | 回收资源、低功耗 |

```text
IMU 定时采集 ──最新值队列──┐
                           ├─通知→ ControlTask → PWM/电机
串口 ISR → 字节队列 → CommandTask ──命令队列──┘

ControlTask / ImuTask ──日志队列──> LogTask
```

### 13.2 为什么这样设计优先级

- ControlTask 有最严格响应时限，但每轮必须非常短，完成后立即阻塞。
- ImuTask 要按固定周期读取数据，优先于指令解析和日志。
- CommandTask 需要及时处理串口，但允许比控制环晚一点。
- LogTask 最低，串口打印绝不能拖慢控制任务。

### 13.3 核心数据结构

```c
typedef struct
{
    float roll;
    float pitch;
    float yaw_rate;
    TickType_t tick;
} ImuSample;

typedef struct
{
    float target_speed;
    float target_yaw_rate;
    uint8_t emergency_stop;
} ControlCommand;

static QueueHandle_t imu_latest_queue;   // 长度 1，只保存最新 IMU
static QueueHandle_t command_queue;      // 长度 1，只保留最新控制目标
static QueueHandle_t uart_rx_queue;      // ISR 到 CommandTask 的字节队列
static QueueHandle_t log_queue;          // 所有实时任务到 LogTask

static TaskHandle_t control_task_handle;
```

### 13.4 IMU 周期任务

```c
static void ImuTask(void *argument)
{
    TickType_t last_wake = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(5); // 200 Hz
    (void)argument;

    for (;;)
    {
        ImuSample sample;

        Imu_ReadAndCalculate(&sample.roll,
                             &sample.pitch,
                             &sample.yaw_rate);
        sample.tick = xTaskGetTickCount();

        xQueueOverwrite(imu_latest_queue, &sample);

        /* 唤醒 ControlTask。通知只表示“有一份新数据”，数据本体在队列中。 */
        xTaskNotifyGive(control_task_handle);

        xTaskDelayUntil(&last_wake, period);
    }
}
```

当 `xTaskNotifyGive()` 使 P4 的 ControlTask Ready 时，它可以立即抢占 P3 的 ImuTask。这正是高优先级控制任务“事件到达即运行”的效果。

### 13.5 控制任务

```c
static void ControlTask(void *argument)
{
    ImuSample imu = {0};
    ControlCommand command = {0};
    (void)argument;

    for (;;)
    {
        /* 没有 IMU/急停事件时 Blocked，不空转占 CPU。 */
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        /* 取最新数据；0 Tick 表示此处不阻塞。 */
        (void)xQueueReceive(imu_latest_queue, &imu, 0);

        /* 命令队列可能没有新命令，保留上一次目标值。 */
        (void)xQueueReceive(command_queue, &command, 0);

        if (command.emergency_stop)
        {
            Motor_StopImmediately();
        }
        else
        {
            MotorOutput output = Controller_Run(&imu, &command);
            Motor_SetOutput(&output);
        }

        /* 严禁在这里 printf；需要记录时，把小型消息投入日志队列。 */
    }
}
```

> [!warning] 一个重要设计细节
> 上面用同一个通知唤醒 ControlTask，表示“需要立即检查状态”。若要严格区分 IMU、急停等多个事件，可使用通知位 `xTaskNotify(..., eSetBits)` 或事件组，并为共享命令设计明确的并发保护。

> [!danger] 急停必须锁存
> 真正的机器人不能只把急停当成一个可能被下一条命令覆盖的普通目标值。应由硬件安全链路或独立的软件锁存状态保持停机，只有满足明确复位条件后才能解除。

### 13.6 UART ISR 与命令任务

```c
void USART1_IRQHandler(void)
{
    BaseType_t higher_priority_task_woken = pdFALSE;

    if (USART_GetITStatus(USART1, USART_IT_RXNE) != RESET)
    {
        uint8_t byte = (uint8_t)USART_ReceiveData(USART1);

        /* ISR 只搬运字节，不在这里解析字符串或执行命令。 */
        (void)xQueueSendFromISR(uart_rx_queue,
                                &byte,
                                &higher_priority_task_woken);
    }

    portYIELD_FROM_ISR(higher_priority_task_woken);
}

static void CommandTask(void *argument)
{
    uint8_t byte;
    CommandParser parser = {0};
    (void)argument;

    for (;;)
    {
        if (xQueueReceive(uart_rx_queue,
                          &byte,
                          portMAX_DELAY) == pdPASS)
        {
            ControlCommand command;

            if (CommandParser_Push(&parser, byte, &command))
            {
                /* 控制目标只需要最新值；队列长度为 1，避免旧命令积压。 */
                xQueueOverwrite(command_queue, &command);

                /* 命令变化后让 ControlTask 尽快重新检查。 */
                xTaskNotifyGive(control_task_handle);
            }
        }
    }
}
```

调用 `xQueueSendFromISR()` 的 USART 中断必须处于 FreeRTOS 允许调用 ISR API 的 NVIC 优先级范围，参见 [[配置文件#7. 中断优先级：最容易出错的部分]]。

### 13.7 初始化顺序

```c
void RobotTasksInit(void)
{
    imu_latest_queue = xQueueCreate(1, sizeof(ImuSample));
    command_queue    = xQueueCreate(1, sizeof(ControlCommand));
    uart_rx_queue    = xQueueCreate(64, sizeof(uint8_t));
    log_queue        = xQueueCreate(16, sizeof(LogMessage));

    configASSERT(imu_latest_queue != NULL);
    configASSERT(command_queue != NULL);
    configASSERT(uart_rx_queue != NULL);
    configASSERT(log_queue != NULL);

    /* 先创建接收通知的任务并保存句柄，再创建可能发送通知的任务。 */
    configASSERT(xTaskCreate(ControlTask, "Control", 384,
                             NULL, 4, &control_task_handle) == pdPASS);

    configASSERT(xTaskCreate(ImuTask, "IMU", 384,
                             NULL, 3, NULL) == pdPASS);

    configASSERT(xTaskCreate(CommandTask, "Command", 384,
                             NULL, 2, NULL) == pdPASS);

    configASSERT(xTaskCreate(StatusTask, "Status", 192,
                             NULL, 1, NULL) == pdPASS);

    configASSERT(xTaskCreate(LogTask, "Log", 384,
                             NULL, 1, NULL) == pdPASS);
}
```

### 13.8 一条真实调度时间线

```text
① ControlTask(P4) 阻塞等待通知
② ImuTask(P3) 周期到期并读取 IMU
③ ImuTask 写入最新值，通知 ControlTask
④ ControlTask 变为 Ready，抢占 ImuTask
⑤ ControlTask 计算并更新 PWM，然后再次阻塞
⑥ ImuTask 从被抢占的位置继续，调用 xTaskDelayUntil 后阻塞
⑦ CommandTask 或低优先级任务获得 CPU
⑧ 若所有业务任务都阻塞，Idle Task 运行
```

如果串口 ISR 在第 ④ 步发生：ISR 先打断 ControlTask，放入一个字节后退出；CommandTask 只有 P2，不会抢占仍为 Ready 的 P4 ControlTask。中断及时收走数据，而控制任务的时限仍优先。

### 13.9 这个架构仍需继续验证什么

- 测量 ControlTask 和 ImuTask 最坏执行时间；
- 检查 5 ms 周期是否出现 deadline miss；
- 统计 UART、命令和日志队列满次数；
- 检查每个任务的栈高水位；
- 明确命令结构在多任务间的所有权；
- 设计传感器异常、通信中断和电机故障时的安全状态。

## 14. 常见错误与设计检查表

### 14.1 高频错误

#### 错误一：任务死循环里没有任何阻塞

```c
for (;;)
{
    CheckKey(); // 永远 Ready，持续消耗 CPU
}
```

应改为外部中断通知、队列等待，或至少合理的周期延时。

#### 错误二：用 `HAL_Delay()` 管理 FreeRTOS 任务周期

调度器启动后，优先使用 `vTaskDelay()`/`xTaskDelayUntil()`。`HAL_Delay()` 与 FreeRTOS Tick 的关系取决于工程移植配置，误用可能忙等待或产生 Tick 冲突。

#### 错误三：优先级越重要就设得越高

“重要”不等于“必须最快响应”。日志很重要，但通常不应抢占电机控制。

#### 错误四：在 ISR 中直接解析协议或打印

ISR 只清中断、搬数据和唤醒任务。复杂工作交给任务。

#### 错误五：频繁 Suspend/Resume 代替事件同步

需求是“等待事件”时，应使用通知、队列或信号量，让任务自然进入 Blocked。

#### 错误六：认为任务被抢占后会重新开始

上下文切换会保存执行现场。任务恢复后从上次位置继续。

#### 错误七：队列里传局部变量指针

FreeRTOS 队列默认按值复制队列项；若队列项是指针，只复制地址。必须保证指向的对象在消费者使用期间仍有效，并定义谁负责释放。

### 14.2 创建任务前

- [ ] 这个模块真的需要独立任务吗？
- [ ] 任务由周期唤醒还是事件唤醒？
- [ ] 没有工作时会进入 Blocked 吗？
- [ ] 优先级是否根据响应时限设计？
- [ ] 栈单位是否理解为 `StackType_t` 而非字节？
- [ ] 参数指针的生命周期是否覆盖任务生命周期？

### 14.3 运行中

- [ ] 是否统计任务栈高水位？
- [ ] 是否观察 FreeRTOS 最小历史剩余堆？
- [ ] 队列满、超时和周期超限是否有计数？
- [ ] 高优先级任务的最坏执行时间是否可控？
- [ ] Idle Task 是否有机会运行？
- [ ] ISR 是否只调用允许的 `...FromISR()` API？

### 14.4 架构复查

- [ ] 数据所有权是否清楚：谁创建、谁修改、谁释放？
- [ ] 共享外设是否用互斥锁或单一所有者任务保护？
- [ ] 是否把慢速日志从实时任务中分离？
- [ ] 是否有任务永远 Ready 导致低优先级任务饥饿？
- [ ] 周期任务是否需要 `xTaskDelayUntil()` 而不是相对延时？
- [ ] 错误路径是否也会释放锁、内存和外设状态？

## 最后一张总图

```text
任务函数
  ↓ xTaskCreate / xTaskCreateStatic
TCB + 独立栈 + 优先级 + Handle
  ↓
Ready ──调度器选择──> Running
  ▲                     │
  │                     ├─ 延时/等事件 → Blocked
  │                     ├─ 显式挂起   → Suspended
  │                     ├─ 被抢占     → Ready
  │                     └─ 删除       → Idle Task 回收
  │
  ├─ 时间到
  ├─ 队列/通知/信号量到达
  └─ 显式恢复

调度规则：最高优先级 Ready 任务运行
设计关键：短工作 + 及时阻塞 + 清楚的数据所有权
```

真正掌握任务管理，不是背诵 API，而是看到一个需求就能回答：

1. 谁负责这项工作？
2. 它应在什么条件下从 Blocked 变成 Ready？
3. 它的响应时限决定什么优先级？
4. 它怎样与其他任务安全传递数据？
5. 它完成一轮工作后怎样尽快释放 CPU？
