FreeRTOS 的 **堆内存管理**，你可以把它理解成：

> FreeRTOS 自己在 SRAM 里划出一块区域，用来给任务、队列、信号量、软件定时器等内核对象动态分配内存。

它和你前面学的普通 C `malloc/free` 很像，但 FreeRTOS 自己提供了一套：

```
pvPortMalloc()
vPortFree()
```

并且配了 5 种不同的 heap 实现：

```
heap_1.c
heap_2.c
heap_3.c
heap_4.c
heap_5.c
```

这部分非常重要，因为你以后遇到：

```
任务创建失败
Queue 创建失败
Malloc Failed
Heap 不够
内存碎片
```

基本都和它有关。

---

## 1. FreeRTOS 为什么需要 Heap？

比如你创建一个任务：

```
xTaskCreate(
    vMotorTask,
    "Motor",
    256,
    NULL,
    3,
    &xMotorTaskHandle
);
```

FreeRTOS 并不是凭空产生一个任务。

它至少需要准备两块东西：

```
Task Control Block
TCB

+

Task Stack
任务栈
```

所以大概：

```
xTaskCreate()
    ↓
pvPortMalloc()
    ↓
申请 TCB
    ↓
申请 Task Stack
```

如果再创建 Queue：

```
xQueueCreate(10, sizeof(int));
```

还要申请：

```
Queue控制结构
+
Queue数据存储空间
```

Mutex：

```
xSemaphoreCreateMutex();
```

也需要内存。

软件定时器：

```
xTimerCreate(...);
```

也需要内存。

所以 FreeRTOS Heap 可以粗略想成：

```
FreeRTOS Heap
│
├── Task1 TCB
├── Task1 Stack
├── Task2 TCB
├── Task2 Stack
├── Queue
├── Semaphore
├── Mutex
├── Timer
└── ...
```

---

# 2. FreeRTOS Heap 在哪里？

通常就在：

> **SRAM**

例如：

```
#define configTOTAL_HEAP_SIZE    (20 * 1024)
```

表示：

```
FreeRTOS 给自己准备约 20KB 的 Heap
```

如果你使用的是 `heap_4.c`，经典实现里会有类似：

```
static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];
```

于是：

```
ucHeap[]
↓
一个巨大的字节数组
↓
位于 SRAM
↓
FreeRTOS 把它当作自己的 Heap
```

所以从链接器角度：

```
ucHeap[]
```

可能只是一个 `.bss` 里的大数组。

但从 FreeRTOS 的角度：

```
这就是我的堆。
```

---

# 3. `configTOTAL_HEAP_SIZE`

这是你必须认识的配置。

例如：

```
#define configTOTAL_HEAP_SIZE    ((size_t)(20 * 1024))
```

表示：

```
20KB
```

FreeRTOS 动态内存池。

假设 MCU 总 SRAM 是：

```
48KB
```

并不意味着 FreeRTOS 可以全部使用。

因为 SRAM 还要放：

```
.data
.bss
普通全局变量
HAL句柄
DMA Buffer
主栈
其他静态数组
```

所以大概可能：

```
48KB SRAM

├── .data/.bss       10KB
├── FreeRTOS Heap    20KB
├── 系统 Stack        4KB
└── 其它空间          14KB
```

这里只是示意。

---

# 4. `pvPortMalloc()` 是什么？

FreeRTOS 的动态内存申请函数：

```
void *pvPortMalloc(size_t xWantedSize);
```

和：

```
malloc()
```

很像。

例如：

```
uint8_t *pBuffer;

pBuffer = pvPortMalloc(100);
```

意思：

```
从 FreeRTOS Heap
申请 100 Byte
```

成功：

```
返回地址
```

失败：

```
NULL
```

所以规范写法：

```
uint8_t *pBuffer;

pBuffer = pvPortMalloc(100);

if (pBuffer == NULL)
{
    // 内存申请失败
}
```

---

# 5. `vPortFree()`

对应释放：

```
vPortFree(pBuffer);
```

就是：

```
这块内存我不用了
↓
归还给 FreeRTOS Heap
```

但是注意：

> 不是所有 heap 实现都支持 `vPortFree()`。

这正好引出 `heap_1 ~ heap_5`。

---

# 6. 为什么 FreeRTOS 要提供 5 种 Heap？

因为嵌入式项目差别特别大。

有的项目：

```
任务启动时一次性创建
之后永不删除
```

那根本不需要 free。

有的项目：

```
频繁创建/删除任务
```

就必须支持释放。

有的系统：

```
RAM 只有一块
```

有的：

```
SRAM1
SRAM2
外部 SDRAM
```

内存不连续。

所以 FreeRTOS 没强迫所有人使用一个复杂 allocator，而是提供了 5 个实现。

---

# 7. heap_1.c

最简单。

核心特点：

> **只能申请，不能释放。**

可以想象：

```
FreeRTOS Heap

起点
↓
┌────────────────────────┐
│ 已使用                  │
├────────────────────────┤
│ 已使用                  │
├────────────────────────┤
│ 已使用                  │
├────────────────────────┤
│ 空闲                    │
└────────────────────────┘
```

每次：

```
pvPortMalloc()
```

就从前往后切一块。

比如：

```
Heap = 1000 Byte
```

第一次：

```
申请100
剩900
```

第二次：

```
申请200
剩700
```

第三次：

```
申请300
剩400
```

但是：

```
vPortFree()
```

不真正释放。

---

# 8. heap_1 的优点

非常明显：

```
实现简单
速度快
时间确定
没有碎片
```

为什么没有碎片？

因为：

```
根本不释放
```

当然就不会出现：

```
一块空
一块占
一块空
```

这种情况。

---

# 9. heap_1 适合什么项目？

例如：

```
上电
↓
创建所有 Task
↓
创建所有 Queue
↓
创建所有 Semaphore
↓
之后永远不再创建/删除
```

这种系统非常适合。

例如：

```
MotorTask
IMUTask
ControlTask
CANTask
```

一上电全部创建好，之后运行几年都不删。

这其实是非常典型的嵌入式思想。

---

# 10. heap_2.c

heap_2 支持：

```
申请
释放
```

比 heap_1 灵活。

但是：

> **不会很好地合并相邻空闲块。**

所以容易产生：

```
Memory Fragmentation
内存碎片
```

---

# 11. 什么叫内存碎片？

假设 Heap：

```
┌─────┬─────┬─────┬─────┐
│ A   │ B   │ C   │ D   │
└─────┴─────┴─────┴─────┘
```

后来释放：

```
B
D
```

变成：

```
┌─────┬─────┬─────┬─────┐
│ A   │ 空  │ C   │ 空  │
└─────┴─────┴─────┴─────┘
```

假设：

```
每块空闲 100 Byte
```

那么总空闲：

```
200 Byte
```

但是如果你申请：

```
150 Byte
```

却可能失败。

为什么？

因为没有：

```
连续 150 Byte
```

虽然总空闲够。

这就是：

> **External Fragmentation，外部碎片。**

---

# 12. heap_2 为什么现在不太推荐？

因为：

```
能 free
但不擅长合并
```

长期运行时：

```
申请
释放
申请
释放
```

容易越来越碎。

所以一般新项目更常考虑：

```
heap_4
```

而不是 heap_2。

---

# 13. heap_3.c

heap_3 很特殊。

它本质上：

> **直接使用 C 标准库的 `malloc/free`。**

大概思路：

```
pvPortMalloc()
{
    malloc();
}
```

```
vPortFree()
{
    free();
}
```

所以 FreeRTOS 不自己维护那块 Heap。

而是：

```
交给 C 运行库
```

---

# 14. heap_3 的优缺点

优点：

```
简单
直接复用 libc
```

缺点：

```
行为依赖 C 库
实时性不好保证
不同编译器实现不同
线程安全特性需要注意
```

对于强调确定性的嵌入式实时系统，不一定是最理想选择。

---

# 15. heap_4.c

这是你最应该重点理解的。

很多 STM32 + FreeRTOS 项目都常见：

```
heap_4.c
```

它特点：

```
支持申请
支持释放
支持相邻空闲块合并
```

也就是：

> 比 heap_2 更好地处理内存碎片。

---

# 16. heap_4 的基本思想

Heap 初始：

```
┌───────────────────────────────┐
│           全部空闲            │
└───────────────────────────────┘
```

申请 100 Byte：

```
┌──────────┬────────────────────┐
│ 100使用  │      剩余空闲      │
└──────────┴────────────────────┘
```

再申请 200：

```
┌──────────┬────────────┬───────┐
│ 100使用  │ 200使用    │ 空闲  │
└──────────┴────────────┴───────┘
```

---

# 17. heap_4 怎么处理释放？

假设：

```
┌──────────┬────────────┬───────────┐
│ A 100    │ B 200      │ C 300     │
└──────────┴────────────┴───────────┘
```

释放 B：

```
┌──────────┬────────────┬───────────┐
│ A        │ 空闲200    │ C         │
└──────────┴────────────┴───────────┘
```

再释放 C：

```
┌──────────┬────────────┬───────────┐
│ A        │ 空闲200    │ 空闲300   │
└──────────┴────────────┴───────────┘
```

heap_4 会发现：

```
两个空闲块相邻
```

于是：

```
200 + 300
↓
合并成一块
```

变成：

```
┌──────────┬───────────────────────┐
│ A        │ 空闲500               │
└──────────┴───────────────────────┘
```

所以碎片问题明显改善。

---

# 18. heap_4 并不是“永远没有碎片”

注意，不要误解。

它能：

```
合并相邻空闲块
```

但如果中间隔着正在使用的块：

```
空闲100
↓
使用200
↓
空闲300
```

它不能跨过：

```
使用200
```

把两边硬合并。

所以仍然可能有：

```
外部碎片
```

只是比 heap_2 好很多。

---

# 19. heap_5.c

heap_5 大体继承 heap_4 的思路：

```
申请
释放
合并
```

但是多了一个非常重要的能力：

> **可以管理多块不连续 RAM。**

例如 MCU：

```
SRAM1
0x20000000
大小64KB

SRAM2
0x20010000
大小32KB

外部RAM
0x60000000
大小1MB
```

这些不是一整块连续区域。

heap_4 更适合：

```
一整块连续 heap
```

heap_5 可以：

```
region1
region2
region3
```

一起管理。

---

# 20. heap_5 什么时候用？

例如：

```
STM32H7
多块 SRAM

或者
外部 SDRAM
```

这时候 heap_5 很有用。

而你现在 STM32F103 学习阶段：

```
heap_4
```

通常更自然。

---

# 21. 五种 Heap 一张表

|实现|申请|释放|合并相邻空闲块|多内存区域|
|---|---|---|---|---|
|`heap_1`|✓|✗|不需要|✗|
|`heap_2`|✓|✓|✗|✗|
|`heap_3`|✓|✓|取决于 C 库|取决于 C 库|
|`heap_4`|✓|✓|✓|✗|
|`heap_5`|✓|✓|✓|✓|

你可以先记：

```
heap_1
最简单

heap_2
支持free但碎片处理弱

heap_3
直接用malloc/free

heap_4
最常见

heap_5
多内存区域
```

---

# 22. 为什么只能选一个 heap_x.c？

因为：

```
heap_1.c
heap_2.c
heap_3.c
heap_4.c
heap_5.c
```

都会实现：

```
pvPortMalloc()
vPortFree()
```

如果你把：

```
heap_1.c
heap_4.c
```

一起编译：

链接器就会发现：

```
pvPortMalloc 被定义两次
vPortFree 被定义两次
```

然后报：

```
multiple definition
```

所以：

> **一次只能编译一个 heap_x.c。**

---

# 23. FreeRTOS 动态创建对象时发生什么？

以任务为例：

```
xTaskCreate(
    vTask1,
    "Task1",
    256,
    NULL,
    2,
    &xTask1Handle
);
```

大概：

```
xTaskCreate()
   ↓
tasks.c
   ↓
pvPortMalloc()
   ↓
heap_4.c
   ↓
申请 TCB
   ↓
申请 Stack
   ↓
初始化任务
```

所以：

```
tasks.c
```

并不需要知道：

```
Heap到底怎么实现
```

它只调用统一接口：

```
pvPortMalloc()
```

至于：

```
heap_1
还是
heap_4
```

由你编译哪个文件决定。

这就是非常经典的：

> **接口和实现分离。**

---

# 24. 为什么这是一个很好的软件设计？

因为 `tasks.c` 只关心：

```
我要申请内存
```

它不用关心：

```
你是不是能free
有没有碎片合并
是不是多块RAM
```

所以：

```
FreeRTOS Kernel
↓
统一接口
pvPortMalloc/vPortFree
↓
不同实现
heap_1~5
```

这种设计非常漂亮。

---

# 25. Heap Block 里面不只有你的数据

这是进一步理解 allocator 的关键。

假设你：

```
pvPortMalloc(100);
```

allocator 可能不仅真正占：

```
100 Byte
```

还需要额外保存：

```
这一块多大
下一块空闲在哪里
是否已分配
```

所以内存块可能类似：

```
┌───────────────┐
│ Block Header  │
│ size          │
│ next pointer  │
├───────────────┤
│ 用户数据100B │
└───────────────┘
```

所以申请：

```
100 Byte
```

实际 Heap 消耗可能：

```
> 100 Byte
```

这叫：

> **allocator metadata 开销。**

---

# 26. 内存对齐

还有一个重要概念：

> **Memory Alignment，内存对齐。**

Cortex-M3 是 32 位 MCU。

CPU 访问：

```
4字节对齐地址
```

通常更自然。

所以你申请：

```
pvPortMalloc(5);
```

allocator 可能不会真的只切：

```
5 Byte
```

可能需要向上对齐，例如：

```
8 Byte
```

再加 Header。

所以：

```
你申请的大小
≠ Heap实际消耗大小
```

---

# 27. 什么叫内存对齐？

比如：

```
0x20000000
0x20000004
0x20000008
```

都是：

```
4字节对齐
```

因为地址能被 4 整除。

而：

```
0x20000001
```

不是。

对齐可以让 CPU：

```
访问更高效
有些平台甚至要求必须对齐
```

---

# 28. `xPortGetFreeHeapSize()`

FreeRTOS 提供：

```
size_t xPortGetFreeHeapSize(void);
```

可以查看：

> 当前还剩多少 FreeRTOS Heap。

例如：

```
size_t xFreeHeap;

xFreeHeap = xPortGetFreeHeapSize();
```

假设：

```
初始 20000
```

创建几个任务后：

```
剩 12500
```

这对调试很有用。

---

# 29. `xPortGetMinimumEverFreeHeapSize()`

这个更有价值。

```
size_t xPortGetMinimumEverFreeHeapSize(void);
```

表示：

> 从系统启动到现在，FreeRTOS Heap 最低曾经剩多少。

比如：

```
当前剩余：
8000 Byte
```

但是历史最低：

```
1200 Byte
```

说明系统某个时刻 Heap 曾经非常紧张。

所以：

```
当前剩多少
```

和：

```
历史最危险时剩多少
```

是两个不同指标。

# 30. Malloc Failed Hook

建议学习项目里打开：

```
#define configUSE_MALLOC_FAILED_HOOK 1
```

然后实现：

```
void vApplicationMallocFailedHook(void)
{
    taskDISABLE_INTERRUPTS();

    for (;;)
    {
    }
}
```

这样如果：

```
pvPortMalloc()
```

失败，FreeRTOS 可以调用这个 Hook。

调试时你就知道：

```
不是任务调度坏了
而是Heap没了
```

# 31. 为什么任务创建失败经常是 Heap 不够？

比如：

```
xTaskCreate(
    vTask1,
    "Task1",
    1024,
    NULL,
    1,
    NULL
);
```

如果 STM32F103：

```
StackType_t = 4 Byte
```

那么：

```
1024 × 4
≈ 4096 Byte
```

光 Task Stack 就约：

```
4KB
```

再加：

```
TCB
内存对齐
allocator metadata
```

所以一次任务可能消耗超过：

```
4KB
```

如果：

```
configTOTAL_HEAP_SIZE = 10KB
```

创建三个这种任务就很可能不够。

---

# 32. Task Stack 和 Heap 的关系再强调一次

动态创建：

```
xTaskCreate()
```

Task Stack：

```
逻辑上：
这是 Stack

物理来源：
从 FreeRTOS Heap 分配
```

所以：

```
Task Stack越大
↓
FreeRTOS Heap消耗越大
```

这就是为什么：

```
xTaskCreate(..., 2048, ...)
```

不能随便把栈写很大。

---

# 33. 静态创建任务就不消耗 FreeRTOS Heap 吗？

例如：

```
xTaskCreateStatic()
```

你自己提前提供：

```
StaticTask_t xTaskBuffer;
StackType_t xStack[256];
```

那么：

```
Task TCB
+
Task Stack
```

由你自己静态提供。

所以这部分：

```
不需要从 FreeRTOS Heap 动态申请
```

这就是静态分配的一个优势。

---

# 34. 动态分配和静态分配怎么选？

动态：

```
xTaskCreate()
```

优点：

```
使用方便
灵活
代码简洁
```

缺点：

```
可能申请失败
Heap需要管理
存在碎片问题
```

静态：

```
xTaskCreateStatic()
```

优点：

```
内存大小编译期确定
不依赖运行时Heap
更容易做确定性设计
```

缺点：

```
写起来稍复杂
需要自己提供Buffer
```

---

# 35. 实时系统为什么喜欢“启动时分配，运行时少分配”？

因为实时系统很在乎：

```
时间确定性
```

假设你的机器人控制循环：

```
每1ms运行一次
```

里面突然：

```
pvPortMalloc(1000);
```

allocator 需要：

```
找空闲块
拆分块
修改链表
```

执行时间可能不是完全固定。

而且长期分配/释放：

```
可能碎片化
```

所以更好的工程思路经常是：

```
系统初始化阶段
↓
把 Task/Queue/Buffer 都创建好
↓
进入正常运行
↓
尽量不频繁 malloc/free
```

---

# 36. 机器人项目里一个典型错误

比如：

```
void vIMUTask(void *pvParameters)
{
    while (1)
    {
        uint8_t *pData =
            pvPortMalloc(512);

        ReadIMU(pData);

        vPortFree(pData);

        vTaskDelay(pdMS_TO_TICKS(5));
    }
}
```

意味着：

```
每5ms
malloc
free
malloc
free
...
```

虽然可能能运行，

但工程上通常不是最佳设计。

更好：

```
void vIMUTask(void *pvParameters)
{
    static uint8_t ucData[512];

    while (1)
    {
        ReadIMU(ucData);

        vTaskDelay(pdMS_TO_TICKS(5));
    }
}
```

或者 Task 创建时一次申请：

```
uint8_t *pData = pvPortMalloc(512);

if (pData == NULL)
{
    vTaskDelete(NULL);
}

while (1)
{
    ReadIMU(pData);

    ...
}
```

然后 Task 删除前再释放。

---

# 37. 什么叫内存泄漏？

例如：

```
while (1)
{
    void *p = pvPortMalloc(100);

    // 没有 vPortFree()
}
```

每次循环：

```
Heap减少100多字节
```

最后：

```
Free Heap = 0
```

这就是：

> **Memory Leak。**

FreeRTOS 运行几分钟没问题，几小时后突然挂，很可能就是这种 bug。

---

# 38. 悬空指针

还有一个 Heap 相关经典错误。

```
uint8_t *p;

p = pvPortMalloc(100);

vPortFree(p);
```

此时：

```
这100字节已经归还Heap
```

但：

```
p
```

里面还保存旧地址。

如果继续：

```
p[0] = 123;
```

就是：

> **Use After Free，释放后继续使用。**

所以释放后经常：

```
vPortFree(p);
p = NULL;
```

更安全。

---

# 39. Double Free

例如：

```
vPortFree(p);

vPortFree(p);
```

同一块内存释放两次。

这可能破坏 allocator 的内部结构。

所以也非常危险。

---

# 40. Heap Overflow 和 Stack Overflow 不一样

### Heap 不够

```
pvPortMalloc()
↓
返回 NULL
```

通常是：

```
Malloc Failed
```

### Stack 不够

```
Task Stack超出边界
↓
覆盖其它内存
```

叫：

```
Stack Overflow
```

两者完全不同。

---

# 41. FreeRTOS Heap 与标准 C Heap 再区分一次

如果你写：

```
malloc(100);
```

通常走：

```
C library Heap
```

如果：

```
pvPortMalloc(100);
```

通常走：

```
FreeRTOS Heap
```

尤其你用：

```
heap_4.c
```

时，两套东西不要混着理解。

如果整个项目已经使用 FreeRTOS，很多嵌入式项目会尽量统一内存策略，避免：

```
一会 malloc
一会 pvPortMalloc
```

导致难以统计 RAM。

# 42. 一个完整内存例子

假设：

```
#define configTOTAL_HEAP_SIZE    (10 * 1024)
```

即：

```
10240 Byte
```

然后：

```
xTaskCreate(
    vTaskA,
    "A",
    256,
    NULL,
    2,
    NULL
);
```

假设 Task Stack：

```
256 × 4
=
1024 Byte
```

再加 TCB 和管理开销。

可能粗略：

```
消耗约1100~1200 Byte
```

再创建：

```
xQueueCreate(
    10,
    sizeof(uint32_t)
);
```

数据区至少：

```
10 × 4 = 40 Byte
```

再加 Queue 控制结构和 allocator 开销。

再创建：

```
xSemaphoreCreateMutex();
```

继续消耗一点。

所以 Heap 会慢慢变：

```
10240
↓
9000
↓
8900
↓
8800
...
```

# 43. 怎么监控 Heap？

你可以定期看：

```
size_t freeHeap;
size_t minHeap;

freeHeap =
    xPortGetFreeHeapSize();

minHeap =
    xPortGetMinimumEverFreeHeapSize();
```

比如调试器看到：

```
freeHeap = 6230
minHeap  = 1780
```

说明：

```
当前还剩6KB

但历史最低只剩1.7KB
```

那就要注意。

# 45. 你真正要记住的核心框架

FreeRTOS Heap：

```
SRAM
↓
FreeRTOS准备一块内存
↓
Heap
↓
pvPortMalloc/vPortFree
↓
给Task/Queue/Semaphore/Timer使用
```

五种实现：

```
heap_1
只申请不释放

heap_2
可释放但不合并

heap_3
直接用C库malloc/free

heap_4
可释放+合并
最常见

heap_5
heap_4 + 多块不连续RAM
```

## 最后把它和你前面所有知识串起来

```
xTaskCreate()
    ↓
tasks.c
    ↓
pvPortMalloc()
    ↓
heap_4.c
    ↓
SRAM中的FreeRTOS Heap
    ↓
分出一块TCB
+
分出一块Task Stack
```

Queue：

```
xQueueCreate()
    ↓
queue.c
    ↓
pvPortMalloc()
    ↓
Heap
```

Software Timer：

```
xTimerCreate()
    ↓
timers.c
    ↓
pvPortMalloc()
    ↓
Heap
```

所以你可以把：

> **FreeRTOS Heap 看成整个内核对象的“内存仓库”。**

而 `heap_1~5` 决定的是：

> **这个仓库到底按照什么规则分货、收货、整理空位。**

这就是 FreeRTOS 堆内存管理的本质。
