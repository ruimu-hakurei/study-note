# 一、为什么 FreeRTOS 要拆成这么多 `.c` 文件？

你可以先把 FreeRTOS 想成一个大型 C 工程。

如果所有东西都写在：

```
FreeRTOS.c
```

里面，那会非常难维护。

所以 FreeRTOS 按功能拆开：

```
tasks.c
```

负责：

> 任务和调度。

```
queue.c
```

负责：

> 队列、信号量、互斥锁。

```
timers.c
```

负责：

> 软件定时器。

```
event_groups.c
```

负责：

> 事件组。

这样不同模块之间职责非常清楚。

---

# 二、最重要的 `tasks.c`

图片里写的是：

```
task.c
```

但现代 FreeRTOS 源码里通常是：

```
tasks.c
```

注意有个 `s`。

这个文件几乎可以认为是：

> **FreeRTOS 内核最核心的文件之一。**

里面实现大量任务相关功能。

比如你之前学过：

```
xTaskCreate()
```

任务创建逻辑主要就在：

```
tasks.c
```

里面。

还有：

```
vTaskDelay()
```

```
vTaskSuspend()
```

```
vTaskResume()
```

```
vTaskDelete()
```

```
vTaskPrioritySet()
```

以及调度器相关：

```
vTaskStartScheduler()
```

本质都和：

```
tasks.c
```

密切相关。

# 三、`tasks.c` 里面到底管理什么？

最重要的是：

```
TCB
```

也就是：

> Task Control Block，任务控制块。

每创建一个任务，FreeRTOS 都需要保存这个任务的信息。

例如：

```
Task1
```

需要保存：

```
任务栈在哪里
当前栈顶在哪里
优先级是多少
任务名称是什么
现在是 Ready 还是 Blocked
等待什么事件
任务通知值是多少
```

这些东西不能凭空消失，所以会放进一个结构体。

可以粗略理解：

```
typedef struct
{
    StackType_t *pxTopOfStack;
    UBaseType_t uxPriority;
    char pcTaskName[...];
    ...
} TCB_t;
```

真实源码更复杂，但思想就是这样。

于是：

```
Task1 → 一个 TCB

Task2 → 一个 TCB

Task3 → 一个 TCB
```

---

# 四、`list.c` 为什么这么重要？

这可能是初学 FreeRTOS 最容易低估的文件。

图片写：

> 用于实现列表数据类型，仅 FreeRTOS 内部使用。

非常准确。

FreeRTOS 内部大量使用：

```
链表
```

管理任务。

比如：

```
Ready List
```

保存：

> 当前已经准备好运行的任务。

还有：

```
Delayed List
```

保存：

> 正在 vTaskDelay() 的任务。

例如现在：

```
TaskA Ready
TaskB Ready
TaskC Blocked 100ms
TaskD Blocked 500ms
```

FreeRTOS 内部不会傻乎乎地每次遍历所有任务。

而是可能组织成：

```
Ready Lists
├── Priority 0
├── Priority 1
├── Priority 2
└── Priority 3
```

再加：

```
Delayed List
```

所以：

```
list.c
```

虽然用户基本不会直接调用，但它实际上支撑着：

```
任务调度
任务阻塞
任务唤醒
事件等待
```

等等。

---

# 五、你之前学的 `vTaskDelay()` 和 list.c 有什么关系？

例如：

```
vTaskDelay(pdMS_TO_TICKS(1000));
```

任务原来在：

```
Ready List
```

里。

执行 Delay 后：

```
Running
↓
Blocked
```

FreeRTOS 会把它从 Ready 相关结构中移走，放到：

```
Delayed List
```

里面。

例如：

```
Task1
Wake Time = Tick 5000
```

等系统 Tick 到：

```
5000
```

再把它拿出来：

```
Delayed List
↓
Ready List
```

所以：

```
tasks.c
```

负责调度逻辑。

而：

```
list.c
```

提供内部的数据结构。

它俩关系非常紧密。

# 六、`queue.c` 是 FreeRTOS 另一个超级重要的文件

图片里写：

> 与队列、各种信号量相关。

这里特别重要。

因为很多初学者以为：

```
Queue
Semaphore
Mutex
```

是三套完全独立的系统。

其实 FreeRTOS 里：

> **信号量和互斥锁在底层大量复用了 Queue 的实现。**

所以：

```
queue.c
```

不只是：

```
队列
```

还涉及：

```
二值信号量
计数信号量
互斥锁
递归互斥锁
Queue Set
```

---

# 七、为什么 Semaphore 可以用 Queue 实现？

我们先看 Queue。

假设：

```
xQueueCreate(5, sizeof(int));
```

表示创建：

```
容量 = 5
每个数据 = int
```

可以想象：

```
┌────┬────┬────┬────┬────┐
│ 12 │ 35 │    │    │    │
└────┴────┴────┴────┴────┘
```

然后：

```
xQueueSend()
```

写数据。

```
xQueueReceive()
```

取数据。

---

二值信号量其实可以抽象成：

```
容量只有 1
```

而且：

```
不关心里面具体存什么数据
```

我们只关心：

```
有 token
还是
没有 token
```

也就是：

```
0 / 1
```

所以可以把二值信号量想象成一种特殊 Queue：

```
空：
没有信号

非空：
有信号
```

这就是为什么它们能共享很多底层机制。

---

# 八、Mutex 为什么也在 `queue.c`？

互斥锁本质上也类似：

```
锁可用
锁被占用
```

所以也能在 Queue 机制基础上实现。

但是 Mutex 比普通 Semaphore 多了非常重要的功能：

```
Priority Inheritance
优先级继承
```

以后你会专门学。

所以：

```
queue.c
```

其实是 FreeRTOS 里一个“大模块”。

你以后看到：

```
xSemaphoreTake()
```

虽然 API 名字写着 Semaphore，

底层最终可能还是走 queue 相关逻辑。

# 九、图片中的 `timer.c`

严格来说通常叫：

```
timers.c
```

不是：

```
timer.c
```

这个文件负责：

> 软件定时器。

比如：

```
xTimerCreate()
```

```
xTimerStart()
```

```
xTimerStop()
```

```
xTimerReset()
```

软件定时器和硬件定时器不是一回事。

比如 STM32：

```
TIM1
TIM2
TIM3
```

这些属于：

> 硬件 Timer。

而：

```
xTimerCreate(...)
```

属于：

> FreeRTOS 软件定时器。

# 十、软件定时器是怎么工作的？

比如：

```
TimerHandle_t timer;

timer = xTimerCreate(
    "LEDTimer",
    pdMS_TO_TICKS(1000),
    pdTRUE,
    NULL,
    TimerCallback
);
```

意思：

```
每 1000ms
↓
执行 TimerCallback()
```

但 FreeRTOS 不会真的为每个 Timer 创建一个 Task。

否则你创建：

```
100 个 Timer
```

岂不是要：

```
100 个 Task
```

太浪费。

FreeRTOS 会创建一个：

```
Timer Service Task
```

然后统一处理软件定时器。

所以：

```
timers.c
```

和：

```
Timer Task
Timer Command Queue
```

有很深关系。

# 十一、`event_groups.c`

它负责：

```
Event Group
事件组
```

你可以把 Event Group 想象成：

> 一组 bit 状态。

例如：

```
bit0 = WiFi连接成功
bit1 = IMU初始化完成
bit2 = CAN初始化完成
bit3 = 电机初始化完成
```

于是一个 32 位值：

```
0000 0000 0000 1111
```

就可以表达多个事件。

例如任务：

```
必须等 IMU + CAN 都初始化完成
```

就可以：

```
等待 bit1 和 bit2
```

常见 API：

```
xEventGroupCreate()
```

```
xEventGroupSetBits()
```

```
xEventGroupWaitBits()
```

实现主要就在：

```
event_groups.c
```

# 十二、`croutine.c` 是什么？

这里是：

```
Co-routine
协程
```

这是 FreeRTOS 比较早期的一套机制。

当年一些 MCU RAM 极小：

```
几 KB RAM
```

创建很多完整 Task 太奢侈。

于是 FreeRTOS 提供 Co-routine。

它比 Task 更轻量。

不过今天：

> 基本已经属于旧技术，不建议新项目使用。

所以你现在学习 FreeRTOS：

```
croutine.c
```

可以知道它是什么，

但是：

> **不用花时间深入。**

STM32 新工程一般直接用 Task。

# 十三、`stream_buffer.c`

这个文件非常值得你以后学。

它支持两个东西：

```
Stream Buffer
Message Buffer
```

注意：

```
Message Buffer
```

虽然头文件可能是：

```
message_buffer.h
```

但是底层其实使用：

```
stream_buffer.c
```

---

# 十四、Stream Buffer 是什么？

特别适合：

> 一端生产字节流，一端消费字节流。

例如：

```
UART DMA
↓
不断收到字节
↓
Stream Buffer
↓
Protocol Task
```

数据：

```
A B C D E F G H...
```

它不太关心：

```
每条消息到底多长
```

强调的是：

```
连续字节流
```

---

# 十五、Message Buffer 是什么？

Message Buffer 则强调：

```
消息边界
```

例如：

```
Message1:
01 02 03

Message2:
AA BB CC DD

Message3:
12 34
```

你发送：

```
3 Byte
4 Byte
2 Byte
```

接收方可以知道每一条消息各自多长。

所以简单记：

```
Stream Buffer
→ 字节流

Message Buffer
→ 一条一条消息
```

# 十七、`.h` 和 `.c` 的关系

例如：

```
task.h
```

可能声明：

```
BaseType_t xTaskCreate(...);

void vTaskDelay(...);
```

而真正的函数实现：

```
BaseType_t xTaskCreate(...)
{
    ...
}
```

在：

```
tasks.c
```

里面。

所以：

```
task.h
   ↓
告诉你“有什么接口”

tasks.c
   ↓
真正实现这些接口
```

这是所有 C 工程非常经典的组织方式。

# 十八、为什么有 `semphr.h`，却没有 `semphr.c`？

这是一个特别值得你注意的问题。

目录里：

```
semphr.h
```

但是你会发现：

```
没有 semphr.c
```

为什么？

因为：

> FreeRTOS Semaphore 底层主要由 Queue 机制实现。

比如：

```
xSemaphoreTake()
```

实际上很多时候是宏或者封装，最终落到：

```
queue.c
```

中的相关函数。

所以：

```
semphr.h
     ↓
Semaphore API
     ↓
queue.c
```

这非常能体现：

> Semaphore 和 Queue 在 FreeRTOS 内核中的深层关系。

# 十九、右边最关键的 `portable`

这部分开始涉及：

> FreeRTOS 为什么能运行在不同 MCU 上。

FreeRTOS 支持：

```
ARM Cortex-M
RISC-V
Xtensa
AVR
...
```

同时还支持：

```
GCC
IAR
Keil/ARM Compiler
Clang
...
```

但 CPU 完全不同。

比如：

```
Cortex-M4
```

任务切换需要：

```
PendSV
PSP
MSP
R0-R15
xPSR
```

但是 RISC-V 完全不是这套。

所以 FreeRTOS 把：

> 和具体 CPU、编译器相关的代码

单独抽出来。

就是：

```
portable
```

---

# 二十、`portable` 这个名字是什么意思？

直接翻译：

```
portable = 可移植的
```

整个思想：

```
FreeRTOS 通用内核
        ↓
      portable
        ↓
适配具体 CPU
```

于是：

```
tasks.c
queue.c
list.c
```

这些基本不用因为：

```
STM32F4
STM32H7
RISC-V
```

而完全重写。

只需要换：

```
port.c
portmacro.h
```

等移植层。

---

# 二十一、`port.c`

这是以后你研究 FreeRTOS 底层最重要的文件之一。

里面通常包含：

```
任务启动
任务上下文切换
中断相关
Tick相关
临界区支持
```

尤其 Cortex-M：

```
PendSV Handler
```

往往和 `port.c` 或对应 port 汇编实现有关。

你之前问过：

```
SysTick
PendSV
SVC
```

它们就和 Port 层有极强关系。

所以：

```
tasks.c
```

更像：

> OS 的通用调度逻辑。

而：

```
port.c
```

负责：

> 怎么让具体 CPU 真正完成调度。

---

# 二十二、举个任务切换例子

假设：

```
Task A Running
```

现在 Task B 优先级更高，并且：

```
Task B Ready
```

调度器：

```
tasks.c
```

做逻辑判断：

```
B 的优先级比 A 高
↓
应该切换任务
```

但是：

> 怎么把 CPU 的寄存器保存下来？

这不是纯 C 的通用逻辑能完全解决的。

Cortex-M 上可能需要：

```
保存 R4-R11
保存 PSP
找到新任务栈
恢复 R4-R11
恢复 PSP
```

这些就是：

```
port.c
portmacro.h
```

负责的地方。

---

# 二十三、所以调度可以看成两层

非常重要：

```
第一层：
tasks.c

决定：
“该换谁运行？”
```

然后：

```
第二层：
port.c

执行：
“具体怎么换？”
```

这个理解非常关键。

可以记：

```
tasks.c
＝政策制定

port.c
＝具体执行
```

# 二十五、`MemMang` 是什么？

图片里：

```

    ├── heap_1.c
    ├── heap_2.c
    ├── heap_3.c
    ├── heap_4.c
    └── heap_5.c
```

它负责：

> FreeRTOS 动态内存管理。

例如你执行：

```
xTaskCreate()
```

```
TCB

```
pvPortMalloc()

# 二十六、为什么有 5 个 Heap？

因为不同嵌入式系统需求不一样。

---

## heap_1

最简单：

```
只能申请
不能释放
```

也就是：

```
malloc ✓
free ✗
```

适合：

```
系统启动时创建完所有东西
以后永不删除
```

优点：

```
极简单
确定性高
```

---

## heap_2

支持：

```
申请
释放
```

但：

> 不会很好地合并相邻空闲块。

所以可能产生：

```
内存碎片
```

现在一般不太推荐。

---

## heap_3

直接封装 C 标准库：

```
malloc()
free()
```

FreeRTOS 自己不真正管理 heap。

因此行为依赖：

```
C运行库
```

---

## heap_4

这个最重要。

很多 STM32 FreeRTOS 项目会用：

```
heap_4.c
```

特点：

```
支持 malloc
支持 free
支持相邻空闲块合并
```

因此能减少内存碎片。

你现在可以先记：

> **普通 STM32 工程看到 heap_4 很正常。**

---

## heap_5

在 heap_4 基础上进一步支持：

> 多块不连续内存区域。

例如 MCU 里：

```
SRAM1
SRAM2
CCM RAM
外部 RAM
```

可能不是连续的一整块。

heap_5 可以管理多个 region。

---

# 二十七、FreeRTOSConfig.h 为什么在图最上面？

这个文件超级重要。

它不是 FreeRTOS 官方统一写死的，而是：

> **由具体工程配置 FreeRTOS。**

例如：

```
#define configUSE_PREEMPTION 1
```

决定：

```
是否使用抢占式调度
```

例如：

```
#define configTICK_RATE_HZ 1000
```

表示：

```
系统 Tick 频率 = 1000Hz
```

也就是：

```
1 Tick = 1ms
```

例如：

```
#define configMAX_PRIORITIES 5
```

表示支持多少任务优先级。

例如：

```
#define configTOTAL_HEAP_SIZE ...
```

决定 FreeRTOS heap 大小。

所以：

```
FreeRTOSConfig.h
```

相当于：

> **你这个 FreeRTOS 工程的总配置文件。**

# 二十九、整个 FreeRTOS 源码可以分成三层

这是这两张图最值得你记住的东西。

## 第一层：应用层

    }

```

以及：

```

```

这些。

## 第二层：FreeRTOS 通用内核

例如：

```

event_groups.c
stream_buffer.c
```

这些与具体 STM32F4 还是 STM32H7 没太大关系。

## 第三层：Port 移植层

例如：

```
portable
↓
GCC
↓
ARM_CM4F
↓
port.c
portmacro.h
```

负责：

```
CPU寄存器
上下文切换
中断
临界区
底层调度
```

所以整体：

```
你的应用程序
     ↓
FreeRTOS API
     ↓
tasks.c / queue.c / ...
     ↓
port.c
     ↓
Cortex-M CPU
```

# 三十、拿 `xTaskCreate()` 完整走一次

以后你调用：

```
xTaskCreate(
    MotorTask,
    "Motor",
    256,
    NULL,
    3,
    NULL
);
```

你现在应该能想象背后发生：

```
用户代码
↓
task.h 找到 API 声明
↓
进入 tasks.c
↓
申请 TCB
↓
申请 Stack
↓
初始化 TCB
↓
初始化任务栈
↓
把任务加入 Ready List
↓
等待 Scheduler 调度
```

其中：

```
申请内存
```

可能去：

```
heap_4.c
```

而：

```
加入链表
```

会使用：

```
list.c
```

所以一次：

```
xTaskCreate()
```

其实已经串起：

```
task.h
tasks.c
list.c
heap_4.c
port.c
```

多个模块了。

# 三十一、再拿 `xSemaphoreTake()` 走一次

例如：

```
xSemaphoreTake(UartMutex, portMAX_DELAY);
```

大概思路：

```
semphr.h
↓
Queue相关接口
↓
queue.c
↓
判断Mutex状态
```

如果锁可用：

```
获得 Mutex
↓
继续运行
```

如果锁不可用：

```
当前任务 Blocked
↓
加入等待列表
↓
Scheduler运行其他Task
```

又会涉及：

```
queue.c
tasks.c
list.c
```

所以你会越来越发现：

> FreeRTOS 这些模块不是互相孤立的。

# 三十二、第二张表里的“必选”怎么理解？

图片里：

```
tasks.c ✓
list.c ✓
```

这是因为：

> 没任务调度就没有 FreeRTOS 的核心。

所以二者必不可少。

而：

```
queue.c
timers.c
event_groups.c
stream_buffer.c
```

在传统手动集成 FreeRTOS 时，是否加入可以视你用不用对应功能而定。

不过现代 FreeRTOS 工程和构建系统经常直接把这些核心源文件都编进去，再通过：

```
FreeRTOSConfig.h
```

关闭不用的特性。

所以你不要机械记成：

```
不用 Queue 就绝对不能编译 queue.c
```

真正项目还是看：

```
FreeRTOS版本
构建方式
配置
```

# 三十四、你现在该掌握到什么程度？

你现在完全没有必要开始逐行看：

```
tasks.c
```

它非常大，一上来容易迷路。

现阶段你只需要建立：

```
tasks.c
→ Task + Scheduler

list.c
→ 内核链表

queue.c
→ Queue + Semaphore + Mutex

timers.c
→ Software Timer

event_groups.c
→ Event Group

stream_buffer.c
→ Stream/Message Buffer

portable
→ CPU/Compiler移植

heap_x.c
→ 动态内存

FreeRTOSConfig.h
→ 工程配置
```

这张对应表特别值得记。

现在它们基本对应：

                tasks.c

        ┌──────────┴──────────┐

    Scheduler                Task
        │                     │
        │                Ready/Blocked
        │                     │
        └──────────┬──────────┘
                   ↓
                 list.c

调度真正落到 CPU：

```

   ↓

   ↓
PendSV
   ↓
保存旧Task现场
   ↓
恢复新Task现场
```

通信：

```
Task A
  ↓
queue.c
  ↓
Queue/Semaphore/Mutex
  ↓
Task B
```

内存：

```

   ↓
tasks.c
   ↓
pvPortMalloc
   ↓
heap_4.c
