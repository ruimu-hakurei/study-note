这张图讲的是 **FreeRTOS 最基本的程序结构：先写任务函数 → 在 `main()` 中创建任务 → 启动调度器**。你可以先把它理解成 FreeRTOS 的“Hello World 框架”。

我们从左到右拆开看。

### 1. 任务函数长什么样

图里第一个任务：

```
void vTask1(void *pvParameters)
{
    ...
}
```

第二个任务：

```
void vTask2(void *pvParameters)
{
    ...
}
```

FreeRTOS 的任务函数一般都写成这种形式：

```
void 任务名(void *pvParameters)
{
    while (1)
    {
        // 任务要不断执行的代码
    }
}
```

这里有两个很重要的地方。

`void` 表示这个函数 **没有返回值**。

```
void vTask1(...)
```

因为 FreeRTOS 任务正常情况下不会像普通函数一样：

```
return;
```

执行完就结束。

任务通常会一直存在，例如：

```
void vTask1(void *pvParameters)
{
    while (1)
    {
        LED_Toggle();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

这个任务的意思就是：

```
翻转 LED
↓
休眠 500 ms
↓
再次运行
↓
翻转 LED
↓
休眠
↓
……
```

---

### 2. `void *pvParameters` 是干什么的

这个地方第一次看很容易迷惑：

```
void vTask1(void *pvParameters)
```

其实就是：

> 创建任务的时候，可以给这个任务传一个参数。

例如：

```
int motor_id = 1;

xTaskCreate(
    vMotorTask,
    "Motor",
    128,
    &motor_id,
    1,
    NULL
);
```

这里：

```
&motor_id
```

会传给：

```
void vMotorTask(void *pvParameters)
```

任务里面就可以取出来：

```
void vMotorTask(void *pvParameters)
{
    int id = *(int *)pvParameters;

    while (1)
    {
        ...
    }
}
```

所以你可以先简单理解：

```
pvParameters
      ↑
创建任务时传进来的数据
```

如果不需要传参数，就直接：

```
NULL
```

这也是截图里的写法。

---

## 3. 为什么任务里面一般必须有 `while(1)`

比如：

```
void vTask1(void *pvParameters)
{
    LED_ON();
}
```

这段代码很危险。

因为执行：

```
LED_ON();
```

之后函数就结束了。

但 FreeRTOS 任务 **不应该像普通 C 函数那样直接返回**。

所以一般写：

```
void vTask1(void *pvParameters)
{
    while (1)
    {
        LED_ON();
    }
}
```

但这样又有一个问题。

这个任务会疯狂执行：

```
LED_ON()
LED_ON()
LED_ON()
LED_ON()
LED_ON()
……
```

CPU 一直被它占着。

所以真实工程一般写：

```
void vTask1(void *pvParameters)
{
    while (1)
    {
        LED_Toggle();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

这才是非常典型的 FreeRTOS 任务。

---

# 4. `vTaskDelay()` 为什么重要

截图中特别提到了：

```
vTaskDelay()
```

例如：

```
void vTask1(void *pvParameters)
{
    while (1)
    {
        LED_Toggle();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

你可以先把它理解成：

> “这个任务暂时不用 CPU 了，500 ms 后再叫我。”

于是系统可能变成：

```
Task1 运行
    ↓
vTaskDelay(500ms)
    ↓
Task1 阻塞
    ↓
CPU 去运行 Task2
    ↓
500ms 到
    ↓
Task1 又变成可运行状态
```

这就是 RTOS 和普通裸机程序非常重要的区别。

整个程序可以分成三个阶段：

```
初始化
  ↓

  ↓
启动调度器
```

# 6. `xTaskCreate()` 是最关键的函数之一

来看这一句：

```
xTaskCreate(vTask1, "Task1", 128, NULL, 1, NULL);
```

它大概长这样：

```
xTaskCreate(
    任务函数,
    任务名字,
    栈大小,
    任务参数,
    优先级,
    任务句柄
);
```

所以：

```
xTaskCreate(vTask1, "Task1", 128, NULL, 1, NULL);
```

分别表示：

|参数|这里的值|意思|
|---|---|---|
|任务函数|`vTask1`|要运行哪个函数|
|名称|`"Task1"`|给任务起名字|
|栈大小|`128`|给任务分配多少栈|
|参数|`NULL`|不传参数|
|优先级|`1`|任务优先级|
|任务句柄|`NULL`|暂时不保存任务句柄|

我们一个个理解。

## 7. 第一个参数 `vTask1`

```
xTaskCreate(
    vTask1,
    ...
);
```

注意这里不是：

```
vTask1()
```

而是：

```
vTask1
```

因为我们不是现在调用它，而是：

> 告诉 FreeRTOS：“以后你帮我运行这个函数。”

本质上这里传的是 **函数地址 / 函数指针**。

可以想成：

```
main()
  |
  | 创建任务
  ↓
FreeRTOS
  |
  | 记住 vTask1 在哪里
  ↓
以后调度的时候调用 vTask1
```

# 8. `"Task1"` 是什么

```
"Task1"
```

只是任务名字。

主要用于：

- 调试
- 查看任务状态
- FreeRTOS Trace
- IDE 调试窗口

它并不是任务真正的变量名。

例如：

```
xTaskCreate(vTask1,
            "LED",
            128,
            NULL,
            1,
            NULL);
```

任务函数叫：

```
vTask1
```

但是调试器中显示：

```
LED
```

也是完全可以的。

# 9. `128` 是任务栈大小

```
xTaskCreate(
    vTask1,
    "Task1",
    128,
    ...
);
```

这意味着 FreeRTOS 给这个任务准备自己的栈。

这是你学习 FreeRTOS 时非常重要的概念：

> **每一个任务都有自己的栈。**

例如系统里：

```
Task1
 └─自己的 Stack

Task2
 └─自己的 Stack

Task3
 └─自己的 Stack
```

任务栈里面会保存：

```
局部变量
函数调用信息
CPU 寄存器现场
返回地址
……
```

例如：

```
void vTask1(void *pvParameters)
{
    int a;
    int buffer[50];

    while (1)
    {
    }
}
```

这些局部变量就会消耗 Task1 的栈。

有一个特别容易踩坑的地方：

> `128` 不一定代表 128 字节。

FreeRTOS 的 `usStackDepth` 通常以 **StackType_t 的个数**计。

例如 STM32 32 位 MCU 中经常：

```
StackType_t = 4 Byte
```

那么：

```
128 × 4 Byte
≈ 512 Byte
```

不过不同移植和 CMSIS-RTOS 封装要具体看，因此以后我们讲任务栈时我会再详细展开。

# 10. 第四个参数 `NULL`

```
NULL
```

对应：

```
void *pvParameters
```

也就是说：

```
xTaskCreate()
        │
        │ pvParameters = NULL
        ↓
vTask1(void *pvParameters)
```

这里任务没有收到任何参数。

---

# 11. 第五个参数 `1`：任务优先级

```
xTaskCreate(
    vTask1,
    "Task1",
    128,
    NULL,
    1,        // 优先级
    NULL
);
```

FreeRTOS 是一个 **基于优先级的抢占式实时操作系统**。

简单理解：

```
优先级 3
↑
优先级 2
↑
优先级 1
↑
优先级 0
```

数字越大，通常优先级越高。

假设：

```
TaskA：优先级 1
TaskB：优先级 2
```

如果两个任务同时 Ready：

```
TaskA Ready
TaskB Ready
```

FreeRTOS 优先运行：

```
TaskB
```

因为：

```
2 > 1
```

---

# 12. 截图里两个任务优先级一样

截图：

```
xTaskCreate(vTask1, "Task1", 128, NULL, 1, NULL);

xTaskCreate(vTask2, "Task2", 128, NULL, 1, NULL);
```

所以：

```
Task1：优先级 1
Task2：优先级 1
```

如果开启时间片调度，它们都处于 Ready 状态时，通常可以轮流获得 CPU：

```
Task1
 ↓
Task2
 ↓
Task1
 ↓
Task2
 ↓
……
```

这就是之后会学习的：

**时间片调度。**

# 13. 最后一个 `NULL` 是任务句柄

完整形式实际上可以这样：

```
TaskHandle_t Task1Handle;

xTaskCreate(
    vTask1,
    "Task1",
    128,
    NULL,
    1,
    &Task1Handle
);
```

之后就可以通过：

```
Task1Handle
```

控制这个任务。

例如以后会学：

```
vTaskSuspend(Task1Handle);
```

暂停任务。

或者：

```
vTaskResume(Task1Handle);
```

恢复任务。

所以句柄可以理解成：

> FreeRTOS 中用来找到某个任务的“身份证 / 引用”。

截图暂时不需要控制任务，所以写：

```
NULL
```

# 14. `vTaskStartScheduler()` 是干什么的

这是整个 FreeRTOS 程序的关键分界线：

```
vTaskStartScheduler();
```

执行之前：

```
CPU 正在执行 main()
```

执行：

```
vTaskStartScheduler();
```

以后：

```
FreeRTOS 调度器接管 CPU
```

开始决定：

```
现在运行 Task1？

还是 Task2？

谁优先级高？

谁正在 Delay？

谁正在等队列？

谁被阻塞？

谁应该被唤醒？
```

你可以把调度器想象成一个交通警察：

```
              调度器
                ↓
      ┌─────────┼─────────┐
      ↓         ↓         ↓
    Task1     Task2     Task3
```

它决定哪个任务获得 CPU。

---

# 15. 一个非常重要的理解：CPU 并不是真的同时运行两个任务

假设 STM32 是单核：

```
Task1
Task2
Task3
```

看起来它们同时运行。

但实际上 CPU 某一瞬间只能运行一个：

```
时间 →

Task1 |████|
Task2      |██|
Task1          |████|
Task3              |██|
Task2                  |██|
```

因为切换非常快，所以你感觉：

```
Task1 在运行
Task2 也在运行
Task3 也在运行
```

这叫：

**并发。**

而不是单核上的真正并行。

这个概念之后理解任务切换特别重要。

# 16. `vTaskStartScheduler()` 后面的 `while(1)` 通常不会运行

截图：

```
vTaskStartScheduler();

while (1)
{
}
```

很多初学者会以为：

```
启动调度器
↓
回来
↓
执行 while(1)
```

通常不是。

正常情况下：

```
vTaskStartScheduler();
```

启动成功之后，FreeRTOS 调度器就开始运行任务，正常情况下不会返回到这里。

也就是：

```
main()
  ↓
创建 Task1
  ↓
创建 Task2
  ↓
vTaskStartScheduler()
  ↓
━━━━ FreeRTOS 世界 ━━━━
Task1
Task2
Idle Task
...
```

如果 `vTaskStartScheduler()` 返回，有时候反而意味着：

**启动调度器失败。**

例如没有足够的内存创建 Idle Task。

所以截图里：

```
while(1){}
```

更多相当于一个兜底。

# 18. 用你以后做机器人来理解

假设你做一个小车。

以前裸机可能：

```
while (1)
{
    Read_IMU();

    Read_Encoder();

    Calculate_PID();

    Control_Motor();

    Send_CAN();

    Send_UART();
}
```

所有事情全塞在一个大循环。

而 FreeRTOS 可以拆：

```
                 FreeRTOS

        ┌──────────┬──────────┐
        ↓          ↓          ↓

     IMU任务     电机任务    通信任务

    读取IMU      PID计算      ROS通信
    姿态解算     控制电机     CAN/UART
```

代码可能变成：

```
void IMUTask(void *arg)
{
    while (1)
    {
        Read_IMU();

        vTaskDelay(pdMS_TO_TICKS(5));
    }
}
```

```
void MotorTask(void *arg)
{
    while (1)
    {
        Motor_PID();

        vTaskDelay(pdMS_TO_TICKS(1));
    }
}
```

```
void CommunicationTask(void *arg)
{
    while (1)
    {
        Send_Data();

        vTaskDelay(pdMS_TO_TICKS(10));
    }
}
```

然后：

```
int main(void)
{
    Hardware_Init();

    xTaskCreate(IMUTask, "IMU", 256, NULL, 3, NULL);

    xTaskCreate(MotorTask, "Motor", 256, NULL, 4, NULL);

    xTaskCreate(CommunicationTask, "COMM", 256, NULL, 2, NULL);

    vTaskStartScheduler();

    while (1);
}
```

这时候你就开始看到 FreeRTOS 的价值了。

## 你现在最需要记住这张图里的 5 件事

```
① 一个 Task 本质上就是一个 C 函数

void Task(void *arg)
```

```
② Task 一般内部有 while(1)

void Task(void *arg)
{
    while(1)
    {
    }
}
```

```
③ 用 xTaskCreate() 创建任务

xTaskCreate(...)
```

```
④ 不同任务可以有不同优先级

Task1：1
Task2：3
```

```
⑤ vTaskStartScheduler() 启动 FreeRTOS 调度
```

把整个启动过程记成这一条线就够了：

```
STM32 上电
   ↓
main()
   ↓
硬件初始化
   ↓
xTaskCreate()
   ↓
xTaskCreate()
   ↓
xTaskCreate()
   ↓
vTaskStartScheduler()
   ↓
━━━━━━━━━━━━━━
 FreeRTOS 调度器开始工作
━━━━━━━━━━━━━━
   ↓
Task A ←→ Task B ←→ Task C
```

下一步最适合学的其实就是 **“任务到底是怎么被调度的：Running、Ready、Blocked、Suspended 四种状态”**。把这个吃透以后，`vTaskDelay()`、优先级、抢占、时间片这些内容会一下子串起来。


这张图其实是在讲 **FreeRTOS 调度器如何在多个任务之间切换 CPU**，核心就是：**任务不是同时执行，而是调度器不断切换。**

左边两个任务分别是 LED1 和 LED3。

第一个任务大概是：

```
void vLED1Task(void *pvParameters)
{
    while(1)
    {
        HAL_GPIO_WritePin(LED1, GPIO_PIN_SET);

        vTaskDelay(pdMS_TO_TICKS(1000));

        HAL_GPIO_WritePin(LED1, GPIO_PIN_RESET);

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

意思就是：

```
LED1亮
↓
任务休眠1000ms
↓
LED1灭
↓
任务休眠1000ms
↓
重复
```

这里最重要的是：

```
vTaskDelay(...)
```

它不是单纯地“让 CPU 原地等”。

而是：

> 让当前任务进入阻塞状态，把 CPU 让给其他任务。

所以当 LED1Task 执行：

```
vTaskDelay(pdMS_TO_TICKS(1000));
```

之后，它自己会暂时停下来，但 CPU 不会停。

CPU 会去执行：

```
LED3Task
其他任务
Idle Task
...
```

这就是 RTOS 特别重要的思想。

---

第二个任务：

```
void vLED3Task(void *pvParameters)
{
    while(1)
    {
        HAL_GPIO_WritePin(LED3, GPIO_PIN_SET);

        vTaskDelay(pdMS_TO_TICKS(300));

        HAL_GPIO_WritePin(LED3, GPIO_PIN_RESET);

        vTaskDelay(pdMS_TO_TICKS(1500));
    }
}
```

它的节奏就是：

```
LED3亮
↓
等300ms
↓
LED3灭
↓
等1500ms
↓
重复
```

所以两个灯虽然都运行在同一个 CPU 上，但可以有完全不同的闪烁周期。

比如：

```
LED1：
亮1000ms → 灭1000ms → 亮1000ms → ...

LED3：
亮300ms → 灭1500ms → 亮300ms → ...
```

调度器会帮你维护它们各自的时间。

## 右边这张调度图怎么理解

右边有：

```
任务1
任务2
任务3
任务4
```

上面是：

```
FreeRTOS调度器
```

不同颜色表示：

> 某个时刻，这个任务正在占用 CPU。

比如黄色部分：

```
任务1正在运行
```

之后任务1可能执行到：

```
vTaskDelay(...)
```

那么它就主动放弃 CPU。

于是：

```
Task1
Running
   ↓
vTaskDelay()
   ↓
Blocked
```

调度器马上去找另一个可以运行的任务。

比如：

```
Task2
```

于是：

```
Task1停止运行

CPU
 ↓

Task2开始运行
```

过了一会儿 Task2 也可能阻塞：

```
Task2
 ↓
vTaskDelay()
 ↓
Blocked
```

然后 CPU 又给 Task3。

所以你看到右边箭头不断在：

```
Task1 → Task4 → Task3 → Task2 → ...
```

之间切换。

这就叫：

**任务切换（Context Switch）**。

## 调度器到底在干什么？

你可以把 CPU 想象成一张椅子。

只有一张椅子：

```
         CPU
      ┌───────┐
      │ 椅子  │
      └───────┘
```

现在有四个人：

```
Task1
Task2
Task3
Task4
```

但任意时刻：

> 只能有一个任务坐在 CPU 这张椅子上。

调度器就是管理员：

```
               调度器
                  ↓

Task1 ──┐
Task2 ──┼──→ CPU
Task3 ──┤
Task4 ──┘
```

它决定：

```
现在谁运行？
谁应该等待？
谁已经Delay结束？
谁优先级最高？
```

# 最关键的概念：任务状态

你现在可以正式开始接触 FreeRTOS 的任务状态了。

最重要的四个：

```
Running
Ready
Blocked
Suspended
```

### Running

正在占用 CPU。

例如：

```
HAL_GPIO_WritePin(...);
```

执行这一行的时候：

```
LED1Task = Running
```

---

### Ready

已经准备好执行，但是 CPU 正被别人使用。

例如：

```
Task1：Ready
Task2：Running
Task3：Ready
```

意思：

```
Task1：我能运行，但是暂时轮不到我

Task2：我现在正在运行

Task3：我也能运行，但是暂时轮不到
```

---

### Blocked

正在等待某件事情。

例如：

```
vTaskDelay(1000);
```

之后：

```
Task1 → Blocked
```

因为它在等：

```
1000ms到期
```

还有以后你会遇到：

```
等待队列
等待信号量
等待事件
等待任务通知
```

这些也会进入 Blocked。

vTaskSuspend(TaskHandle);

## 这张图其实可以画成状态转换

比如 LED1：

```
             调度器选中
Ready  ─────────────────→ Running
 ↑                         │
 │                         │ vTaskDelay()
 │                         ↓
 └────────────────────── Blocked
       1000ms到期
```

这张图你以后会无数次遇到。

特别重要。

# `vTaskDelay()` 到底发生了什么？

假设现在：

```
0ms
```

LED1Task 正在运行：

```
HAL_GPIO_WritePin(...);

vTaskDelay(pdMS_TO_TICKS(1000));
```

执行到：

```
vTaskDelay(...)
```

FreeRTOS 会记住：

```
当前Tick = 100

需要Delay = 1000 Tick

唤醒时间 = 1100
```

然后：

```
LED1Task
Running
↓
Blocked
```

CPU立刻切给别人。

不是：

```
CPU傻等1000ms
```

而是：

```
0ms
LED1运行

1ms ~ 999ms
CPU可以运行别的任务

1000ms
LED1重新变成Ready
```

这个区别非常关键。

---

# 为什么不用 HAL_Delay()？

这也是学 FreeRTOS 必须理解的。

假设写：

```
HAL_Delay(1000);
```

很多情况下，本质思路更接近：

```
CPU一直等待
```

而：

```
vTaskDelay(1000);
```

是：

```
当前任务等待

但是CPU可以做别的事情
```

所以：

```
HAL_Delay
```

更像：

```
你坐在教室里等1000ms
期间什么都不干
```

而：

```
vTaskDelay
```

更像：

```
你告诉老师：
“1000ms以后叫我。”

然后老师去安排别人干活。
```

在 RTOS 任务里面通常更应该使用：

```
vTaskDelay()
```

而不是用普通阻塞式延时。

# 现在再看下面的创建任务

截图里面是类似：

```
xTaskCreate(
    vLED1Task,
    "LED1",
    128,
    NULL,
    1,
    NULL
);
```

然后：

```
xTaskCreate(
    vLED3Task,
    "LED3",
    128,
    NULL,
    1,
    NULL
);
```

两个任务：

```
LED1Task 优先级 = 1
LED3Task 优先级 = 1
```

优先级一样。

因此如果：

```
LED1Task Ready
LED3Task Ready
```

两个都准备运行，FreeRTOS 可以利用时间片让它们轮换。

不过在这个例子里，它们经常执行：

```
vTaskDelay()
```

所以实际上更多时候是：

```
LED1运行一下
↓
LED1 Blocked

LED3运行一下
↓
LED3 Blocked

可能运行Idle Task
↓
某个Delay时间到
↓
那个任务重新Ready
```

# 举个完整时间线

假设刚启动：

```
t = 0ms
```

LED1Task：

```
LED1打开
Delay 1000ms
```

LED3Task：

```
LED3打开
Delay 300ms
```

那么：

```
t = 0ms

LED1Task运行
↓
LED1 ON
↓
Delay 1000ms
↓
Blocked
```

马上：

```
LED3Task运行
↓
LED3 ON
↓
Delay 300ms
↓
Blocked
```

现在两个任务都 Blocked。

CPU怎么办？

还有一个系统自带任务：

```
Idle Task
```

所以：

```
0~300ms
Idle Task运行
```

到了：

```
300ms
```

LED3Task 的 Delay 到期。

于是：

```
LED3Task
Blocked → Ready
```

调度器让它运行：

```
LED3 OFF
↓
Delay 1500ms
```

再次 Blocked。

然后到了：

```
1000ms
```

LED1Task醒来：

```
LED1 OFF
↓
Delay 1000ms
```

所以你最终看到两个 LED：

```
LED1：
ON ━━━━━━━━━ 1000ms
OFF ━━━━━━━━━ 1000ms

LED3：
ON ━━━ 300ms
OFF ━━━━━━━━━━━━━━━ 1500ms
```

但它们背后的 CPU 其实一直在：

```
LED1Task
   ↓
LED3Task
   ↓
Idle
   ↓
LED3Task
   ↓
Idle
   ↓
LED1Task
   ↓
...
```

---

## 你现在一定要建立这个脑图

以后看到：

```
vTaskDelay(...)
```

不要想成：

```
程序停住了
```

应该立刻想到：

```
当前任务：

Running
   ↓
Blocked

CPU：
交给调度器
   ↓
调度器选择其他Ready任务
   ↓
运行其他任务
```

这是 FreeRTOS 最核心的思维之一。

而你这张图右边那些不同颜色，其实就是在表达：

> **CPU 使用权不断从一个任务切换到另一个任务。**

等你把这个理解透，下一步学 **抢占式调度、优先级和时间片** 就会非常顺。
