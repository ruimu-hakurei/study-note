> **SRAM 不是杂乱地塞变量，而是由链接器按照不同用途划分成若干区域（section/段）。**

图里画的是一个简化模型：

```
SRAM
低地址                                              高地址
↓                                                     ↓

┌────────┬────────┬────────┬────────────┬─────────┐
│ .data  │ .bss   │ .heap  │ 未分配区域 │ .stack  │
└────────┴────────┴────────┴────────────┴─────────┘
```

实际工程的布局可能有所不同，但这个模型非常适合先理解。

---

## 1. `.data`：有初始值的全局变量和 static 变量

例如：

```
int a = 10;

static int b = 20;
```

它们有两个特点：

```
生命周期：
整个程序运行期间一直存在

运行过程中：
可以修改
```

比如：

```
a = 100;
b = 200;
```

所以真正运行时必须放：

```
SRAM
```

因此：

```
a
b
↓
.data
↓
SRAM
```

但是这里有个特别关键的问题：

> STM32 刚上电的时候 SRAM 里的数据是不可靠的，那 `10` 和 `20` 从哪里来？

答案是：

```
Flash
```

程序烧录的时候，会把初始值保存到 Flash。

例如：

```
Flash
┌──────────────┐
│ a初始值 = 10 │
│ b初始值 = 20 │
└──────┬───────┘
       │
       │ 上电启动
       ↓
SRAM
┌──────────────┐
│ .data        │
│ a = 10       │
│ b = 20       │
└──────────────┘
```

所以 `.data` 有点特殊：

> **运行位置在 SRAM，但初始值还要在 Flash 中保存一份。**

这叫做：

```
Load Address → Flash
Run Address  → SRAM
```

以后你看 linker script 会真的看到这种概念。

---

## 2. `.bss`：没有初始值或初始化为 0 的全局/static 变量

例如：

```
int a;

static int b;

int c = 0;
```

它们通常进入：

```
.bss
```

运行时同样位于：

```
SRAM
```

但是 `.bss` 和 `.data` 最大区别在于：

```
.data
需要从 Flash 复制初值

.bss
只需要启动时清零
```

例如：

```
int counter;
```

程序开始运行之前，启动代码做：

```
counter = 0
```

并不需要 Flash 专门保存：

```
0 0 0 0 0 0 0 0...
```

这样就可以节省 Flash。

所以启动过程可以理解成：

```
Reset
  ↓
.data：Flash → SRAM
  ↓
.bss：全部清零
  ↓
进入 main()
```

---

# 3. 为什么 `static` 局部变量不在栈里？

这是图片下面特别注明的：

> 栈中的局部变量“不包括静态局部变量”。

例如：

```
void func(void)
{
    int a = 10;

    static int count = 20;
}
```

这里：

```
a
```

是普通局部变量，通常属于：

```
Stack
```

但是：

```
count
```

虽然写在函数里面，却有：

```
static
```

所以它的生命周期是：

> 整个程序运行期间一直存在。

因此它不能随着函数退出就消失。

它一般进入：

```
.data
```

因为：

```
static int count = 20;
```

有非零初值。

如果：

```
static int count;
```

则通常：

```
.bss
```

所以一定要区分：

```
局部变量
≠ 一定在栈

static局部变量
→ .data / .bss
```

# 4. `.heap`：堆

图片中间：

```
.heap
```

对应：

```
malloc()
```

比如：

```
int *p = malloc(100);
```

这里有两个东西。

首先：

```
p
```

如果它是函数里的普通局部变量：

```
p本身
→ Stack
```

但是：

```
malloc(100)
```

申请出来的那 100 字节：

```
Heap
```

也就是：

```
SRAM

Stack
┌────────────┐
│ p          │──────┐
└────────────┘      │
                    ↓
Heap            ┌───────────┐
                │ 100 Byte  │
                └───────────┘
```

所以：

> **指针在哪里，和它指向的数据在哪里，是两个不同的问题。**

这个以后学嵌入式特别重要。

---

# 5. Heap 为什么叫“动态内存”？

因为它不是编译的时候就完全决定好了：

```
int a;
int buffer[100];
```

这些大小基本编译时就知道。

但是：

```
malloc(size);
```

这个 `size` 可以运行时才决定。

例如：

```
uint32_t size = GetPacketSize();

uint8_t *buffer = malloc(size);
```

程序运行到这里才知道申请多少内存。

所以 Heap 是：

> **运行时动态分配区域。**

---

# 6. `free()` 又是干什么？

例如：

```
int *p = malloc(100);

...

free(p);
```

就是：

```
Heap
申请100 Byte
    ↓
使用
    ↓
free()
    ↓
把这块空间归还
```

之后其它 `malloc()` 可以重新使用。

如果一直：

```
malloc()
malloc()
malloc()
```

却不：

```
free()
```

就可能发生：

> **内存泄漏。**

最后 Heap 用完。

---

# 7. `.stack`：栈

图片右边：

```
.stack
```

主要用于：

```
函数参数
普通局部变量
函数调用信息
返回地址
部分寄存器现场
```

例如：

```
void func(int x)
{
    int a = 10;
    int buffer[20];

    anotherFunc();
}
```

概念上：

```
Stack
│
├── x
├── a
├── buffer[20]
├── 返回地址
└── 其它函数调用现场
```

函数结束：

```
func()
  ↓
return
```

这些栈空间就可以被重新使用。

这和 static 完全不同。

---

# 8. 为什么普通局部变量特别适合 Stack？

例如：

```
void Calculate(void)
{
    int a;
}
```

只有进入：

```
Calculate()
```

的时候才需要 `a`。

函数退出之后：

```
a已经没意义了
```

所以非常适合：

```
进入函数
↓
在Stack分配

退出函数
↓
自动回收
```

根本不用你：

```
free(a);
```

这就是栈特别方便的地方。

---

# 9. Stack 和 Heap 最大区别

可以这样理解。

### Stack

```
自动管理
速度快
生命周期通常跟函数调用相关
空间比较有限
```

例如：

```
int x;
int buffer[20];
```

---

### Heap

```
动态管理
需要 malloc/free
生命周期由程序员控制
比较灵活
可能产生碎片
```

例如：

```
uint8_t *buffer = malloc(1000);
```

# 10. 图里的“未分配区域”是什么？

这部分非常重要。

```
.data
.bss
.heap
        ← 还有一些空闲空间 →
.stack
```

说明 SRAM 并不是一定全部被占满。

比如 STM32 有：

```
48 KB SRAM
```

可能：

```
.data + .bss = 8KB

Heap = 10KB

Stack预留 = 4KB
```

中间还可能剩：

```
26KB
```

当然真实 linker script 不一定就严格按照图中这个比例划分。

---

# 11. 为什么 Stack 和 Heap 经常画在两边？

传统内存模型经常画成：

```
低地址

.data
.bss

Heap
 ↓
 ↓
 ↓

空闲区域

 ↑
 ↑
 ↑
Stack

高地址
```

也就是：

```
Heap → 往高地址增长

Stack → 往低地址增长
```

两边向中间靠。

因此如果：

```
Heap越来越大
+
Stack越来越大
```

极端情况下可能互相撞上。

当然具体 STM32 工程怎么布置，还要看：

```
linker script
```

不能把这张教学图理解成所有 MCU 的绝对物理布局。

# 12. 在 STM32CubeIDE 里是谁决定这些段放哪？

答案：

> **链接脚本 Linker Script。**

你在 STM32CubeIDE 工程左侧通常能看到类似：

```
STM32F103RCTX_FLASH.ld
```

这个：

```
.ld
```

就是 GNU linker script。

它会告诉链接器：

```
FLASH 从哪里开始
FLASH 多大

RAM 从哪里开始
RAM 多大

.text 放哪里
.data 放哪里
.bss 放哪里
stack/heap 怎么预留
```

例如你以后可能看到类似：

```
MEMORY
{
    RAM   (xrw) : ORIGIN = 0x20000000, LENGTH = 48K
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 256K
}
```

这非常有意义。

STM32 典型地址：

```
Flash
0x08000000...

SRAM
0x20000000...
```

所以你在 Debug 窗口看一个变量地址：

```
0x2000xxxx
```

往往马上就能判断：

> 这是 SRAM 里的东西。

# 13. Flash 自己也有“段”

这张图只画 SRAM，但完整程序还有 Flash：

```
FLASH
│
├── .isr_vector
│    中断向量表
│
├── .text
│    程序代码
│
├── .rodata
│    字符串/只读常量
│
└── .data 的初始化镜像
```

而 RAM：

```
SRAM
│
├── .data
├── .bss
├── Heap
└── Stack
```

所以完整结构是：

```
                 STM32

       FLASH                    SRAM

┌───────────────────┐    ┌─────────────────┐
│ .isr_vector       │    │ .data           │
├───────────────────┤    ├─────────────────┤
│ .text             │    │ .bss            │
│ 程序代码           │    ├─────────────────┤
├───────────────────┤    │ Heap            │
│ .rodata           │    │                 │
│ 字符串、只读常量    │    │                 │
├───────────────────┤    │                 │
│ .data初始值        │    │                 │
└───────────────────┘    ├─────────────────┤
                         │ Stack           │
                         └─────────────────┘
```

# 14. 到这里就可以开始和 FreeRTOS 联系起来了

这里特别重要。

你这张图画的是传统 C 程序：

```
Heap
Stack
```

但加入 FreeRTOS 以后，事情变得更有意思。

每个 Task 都需要：

> **自己的 Task Stack。**

例如：

```
Task1
→ Stack1

Task2
→ Stack2

Task3
→ Stack3
```

所以不是整个 FreeRTOS 系统只有一个：

```
.stack
```

那么简单。

# 15. FreeRTOS Task Stack 在哪里？

例如：

```
xTaskCreate(
    MotorTask,
    "Motor",
    256,
    NULL,
    2,
    NULL
);
```

如果使用：

```
heap_4.c
```

动态创建任务，那么 FreeRTOS 会从自己的 Heap 中申请：

```
TCB
+
Task Stack
```

大概：

```
SRAM

┌─────────────────────────┐
│ .data                   │
├─────────────────────────┤
│ .bss                    │
│                         │
│ FreeRTOS ucHeap[]       │
│   ├── Task1 TCB         │
│   ├── Task1 Stack       │
│   ├── Task2 TCB         │
│   ├── Task2 Stack       │
│   ├── Queue             │
│   └── Mutex             │
├─────────────────────────┤
│ 其它内存                │
├─────────────────────────┤
│ MSP / main Stack        │
└─────────────────────────┘
```

这里有一个非常重要的修正：

> **FreeRTOS 动态创建出来的 Task Stack，通常不是图片最右边传统意义上的 `.stack` 区域。**

如果使用 `heap_4.c`，它们往往来自：

```
FreeRTOS Heap
```

# 16. FreeRTOS Heap 和 C 的 malloc Heap 又是不是同一个？

**不一定。**

这个非常容易混。

标准 C：

```
malloc()
free()
```

使用的是 C 运行库 Heap。

FreeRTOS：

```
pvPortMalloc()
vPortFree()
```

如果用：

```
heap_4.c
```

通常管理的是 FreeRTOS 自己的一块内存。

例如：

```
static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];
```

概念上就是：

```
SRAM
↓
一个大数组 ucHeap[]
↓
FreeRTOS自己管理
```

然后：

```
xTaskCreate()
```

内部调用：

```
pvPortMalloc()
```

从这里分内存。

所以你以后一定要区分：

```
malloc/free
→ C运行库Heap

pvPortMalloc/vPortFree
→ FreeRTOS Heap
```

虽然某些配置方式下它们可能有联系，但不要默认认为它们永远就是同一块内存。

# 17. `ucHeap[]` 本身为什么可能在 `.bss`？

这个问题非常漂亮。

假设 `heap_4.c` 内部有：

```
static uint8_t ucHeap[20000];
```

而且没给非零初值。

那么从 linker 的角度：

```
ucHeap[]
↓
一个巨大的未初始化static数组
↓
.bss
↓
SRAM
```

但是从 FreeRTOS 的逻辑角度：

```
ucHeap[]
↓
被当作FreeRTOS Heap使用
```

所以：

> **“段”和“内存用途”其实是两个层面的概念。**

`.bss` 是链接器层面的分类。

`FreeRTOS Heap` 是 FreeRTOS 对这块 RAM 的用途定义。

这个理解已经开始比较接近真实工程了。

# 18. 给你几个变量，看看应该去哪

假设：

```
int a = 10;

int b;

static int c = 20;

const char *message = "Hello";

void Task(void)
{
    int x = 100;

    static int count = 0;

    int *p = malloc(40);
}
```

概念上可以分析：

|对象|位置|
|---|---|
|`a`|`.data` → SRAM|
|`b`|`.bss` → SRAM|
|`c`|`.data` → SRAM|
|`message` 全局指针本身|`.data` → SRAM|
|`"Hello"`|`.rodata` → Flash|
|`x`|Stack → SRAM|
|`count`|`.bss` → SRAM|
|`p` 指针本身|Stack → SRAM|
|`malloc(40)` 得到的空间|Heap → SRAM|
|`Task()` 的机器指令|`.text` → Flash|

如果你能自己分析这一张表，说明你已经真正开始掌握 MCU 内存模型了。

## 你现在先记住这一张核心图

```
                   编译后的STM32程序

            ┌──────────┴──────────┐
            ↓                     ↓

          FLASH                  SRAM
            │                     │
      ┌─────┴─────┐       ┌──────┼───────┐
      ↓           ↓       ↓      ↓       ↓
    .text      .rodata   .data   .bss   Heap/Stack
      │           │       │      │       │
    代码         常量    有初值   0值    动态/局部
```

然后再进一步：

```
普通C程序
Stack
→ main和函数的局部变量

FreeRTOS
→ 每个Task还有自己的Task Stack
→ 动态Task Stack通常从FreeRTOS Heap分配
```

这就是为什么你现在学习 `.data/.bss/.heap/.stack` 非常有必要——**接下来一旦讲 `configTOTAL_HEAP_SIZE`、`xTaskCreate()`、Task Stack、TCB、Stack Overflow，这些知识会全部连起来。**
